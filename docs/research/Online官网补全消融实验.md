# Online 官网补全消融实验

## 结论

2026-09-06 的真实网络样本支持删除 Online 的 50 条切片和插件专用批预算，官网采用共享有界并发；单站采用一个总超时，移除独立的 curl 请求超时。建议起点为每进程 50 路、取得名额后单站总时限 12 秒，尚不代表生产容量或最优参数。

保留缓存、域名去重、安全校验、取消传播及父任务期限。不新增独立补全任务、二次 CSV、每 item 信号量、跨任务锁或独立代理池。提案与批准状态见 [003 实施清单](../feat/014.Maps云端/plans/003.可选联系方式与独立采集库.md)。

## 方法与边界

- 基线为现有 `MapsEnrichProvider.enrich`，源码版本 `b8869ee131ff8d15ec575def7be13a0cbaa172ab`；没有实现尚不存在的采集库或修改应用源码。
- 数据来自 [Little Rock 采集 CSV](gmaps-rpc-data/stress_batch500/Restaurant_Little_Rock_US.csv)，依原顺序选取前 60 个不同 Website 主机，保留路径。原始 Maps 字段包含一个 Facebook 地址及部分商家平台页面，不能声称样本都是独立商家官网；没有继续访问从 HTML 提取出的社媒外链。
- 实验进程通过真实 Cloudflare HTTPS DNS 获取 A／AAAA，保留所有返回地址及既有公网判定；60 个初始主机预解析成功，重定向继续校验。该适配仅用于避开本机 Fake-IP，未修改系统 DNS 或关闭 SSRF。
- 在 `curl_cffi` 网络出口显式传入只读取得的现有代理，按初始主机固定代理分配，同一个网站的重定向保持该代理。没有替换 HTTP 内容或模拟响应。
- Redis 真实运行，每个实验使用独立前缀；冷读组不共享应用缓存，复测增加一次热读。两个运行前缀最终剩余键数均为 0；未操作数据库业务记录、任务表、OSS 或配置表。
- 自变量为切片大小、信号量名额、批超时、外层单站超时及 curl 超时；改变实验进程中的对应值，继续运行同一套现有采集和解析代码。
- HTML 成功数按成功写入缓存的主机计数，包含成功访问但无联系方式的页面；联系方式数按至少产出一项 Email 或社媒链接的主机计数，不证明逐项准确率。请求数包含重定向。

## 首轮逐项消融

1. **现有基线**：50 条切片、5 路并发、批超时 25 秒、单站外层 12 秒、curl 8 秒。耗时 **24.090 秒**，HTML 成功 **17/60**，有联系方式 **14/60**，发出 33 次请求，单站超时 42 次。
2. **仅删除批超时**：其余同基线。耗时 **24.023 秒**，HTML 成功 **17/60**，有联系方式 **15/60**，34 次请求，单站超时 42 次。本组没有观察到批预算收益。
3. **再删除 50 条切片**：全组处理，仍为 5 路。耗时 **12.011 秒**，HTML 成功 **10/60**，有联系方式 **9/60**，22 次请求，单站超时 48 次。更快来自大量任务在排队时耗尽 12 秒，不能当作效率改善。
4. **共享并发提高到 50**：全组、无批超时，保留外层 12 秒与 curl 8 秒。耗时 **11.714 秒**，HTML 成功 **54/60**，有联系方式 **43/60**，85 次请求。
5. **只保留外层单站超时**：在上一组基础上将 curl 超时设为 None。耗时 **9.521 秒**，HTML 成功 **54/60**，有联系方式 **43/60**，85 次请求。
6. **名额放开到整个样本的 60 路**：其他同上一组。耗时 **11.239 秒**，HTML 成功 **54/60**，有联系方式 **43/60**，85 次请求；未观察到更多产出。

现有 `curl_cffi` 对流式请求的数值超时配置连接超时与低速检测，不能误写成绝对单请求总时限；None 将其关闭。库内总时限由外层异步期限承担。核实入口为当前安装包的 `curl_cffi/requests/utils.py`，源依赖见 `backend/uv.lock`。

## 反序复测与缓存

为减少固定执行顺序造成的误判，只复测最终两个候选，顺序改为 60 路后 50 路：

- **60 路**：12.059 秒，HTML 成功 53/60，有联系方式 42/60，85 次请求。
- **50 路**：12.023 秒，HTML 成功 53/60，有联系方式 42/60，83 次请求。
- **50 路缓存热读**：53 个主机已有成功缓存，7.138 秒、11 次请求，有联系方式 43/60；已缓存结果逐项一致，之前失败的目标仍会重新请求。缓存确实减少外网请求，不删除。

外网成功数有波动，不能将首轮 9.521 秒相对 11.714 秒的差异归因于删除 curl 超时。可以确认的是：两轮样本中，50 路相对 60 路未减少成功主机或联系方式主机数量，因此没有必要据此取消并发上限。

## 设计删减

- **删除 Online 50 条切片**：其来源是插件请求 schema 的单次入参数量；内部 `enrich` 无此限制。整 item 一次交给编排即可，不增加新批处理抽象。
- **删除 Online 25 秒批预算**：它服务于插件 30 秒 RPC。插件仍保留其调用方响应预算，Online 复用父任务期限，不再增加一层批取消。
- **单站只保留总超时**：保留有限重定向、大小上限和安全校验，删除单独 curl 超时；编排先取得信号量名额，再调用有总时限的单站库。
- **独立库保持单站能力**：一个异步公开函数和一个结果类型，不带缓存、池管理、账号、批模型或调度器；本项目沿用现有补全 Provider 承担这些业务编排。
- **保留域名去重**：本轮采样已选不同主机，没有用实验测量它的收益；从现有分组代码可确认同批重复主机共用抓取。删除 Online 切片后，去重范围自然扩大至整个 item，不增加跨任务协调。

实验中的 12 秒仍包住队列等待；“取得名额后再计时”属于已批准的目标设计，尚未实现，不能把本次结果记为该实现已验收。父任务到期仍沿用整个未完成 item 的原失败行为，不新增保底 CSV、交付预留时间或补偿。

## 复现与限制

本地实验脚本和原始结果保存在不入 git 的 `docs/scratch/`：`contact_ablation.py`、`contact-ablation-results.json`、`contact-ablation-confirm-results.json`。在 `backend/` 执行 `uv run python ../docs/scratch/contact_ablation.py`，反序复测加 `--confirm`。它们是本轮实验材料，不是生产采集库或新回归测试套件。

本轮共 9 组观测，只有最终候选进行了反序复测；未覆盖多进程、多用户长期负载、代理总限额、峰值内存及延迟分位数，不承诺最高吞吐。只验证了当前样本的可用性、产出数量和请求数，没有生成 Online CSV 或运行完整任务／计量链，也没有验收新库的独立打包。
