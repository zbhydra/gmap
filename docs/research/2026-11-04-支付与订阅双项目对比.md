# gmap 与 extension-tg-download 支付、订阅对比

这是 2026-11-04 对两份本地工作区源码的比较，用于确定 Stripe 接入的复用边界。没有查询数据库、检查线上配置或执行真实支付；发布记录中的可售商品只代表仓库配置基线。

## 结论

两个项目共用同源的订单与支付底座：配置验价 → 本地订单快照 → Provider 创建支付入口 → 渠道验签或查单 → 统一订单回调 → 事务内发放权益；每次续费单独落订单，渠道流水唯一约束与订单 CAS 收敛重复付款通知。

gmap 已扩展出多产品线、多档位、折算升级与渠道协议换价。TG 按插件与 App 隔离订阅，提供不同周期、终生权益和 Google Play 支付；App 的升级是放行更高周期商品的全价购买，不是 gmap 的补差升级。两边都没有 Stripe Provider。

## 支付流程

| 项目                 | gmap                                                                                                                            | extension-tg-download                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 已实现渠道           | PayPal、ClinkBill、Telegram Stars                                                                                               | 同左，另有 Google Play                                                                  |
| 普通下单             | `order_client.create_order` 调共享 `order_service.create_order_with_payment`；升级差额下单复用它                                | 创建订单、调用 Provider、保存支付数据、装配响应都在 `order_client.create_order`         |
| 计费配置             | 商品拥有 `auto_renew / period`；渠道价拥有金额、币种、SKU 与自动续费支持标志                                                    | 相同，不是每个渠道独立选择商品计费模式                                                  |
| PayPal 收款确认      | Webhook 与登录后的 `/order/paypal/confirm` 共用收款核对和幂等履约；回跳可主动查询并收款                                         | 首期依赖 Webhook 触发收款；网站 success 回跳只轮询本地订单，无对应主动确认接口          |
| 停售后的回调         | PayPal / Clink 均读取历史支付配置，不要求渠道仍启用                                                                             | Clink 读取历史支付配置；PayPal 回调仍调用只读启用渠道的 `get_provider`                  |
| Clink 一次性对账     | 使用 `amountTotal / paymentCurrency` 核对订单                                                                                   | 使用 `originalCurrency` 与 `priceDataList` 原商品金额核对；支付换汇金额另记             |
| Clink Order 回调应答 | 核对一次性及 recurring Order，并按账户事件返回 `account.reloaded`                                                               | recurring Order 直接确认接收；回调返回项目统一 envelope                                 |
| Clink 订阅实付       | 首期、续费和折算付款由 `invoice.paid` 进入统一订单回调；折算金额不再强制等于首单整期价格                                        | 同样只用 `invoice.paid` 发放订阅，但发票金额仍须等于首单价格，未接入折算付款            |
| 支付失败恢复         | 有 `retryable / non_retryable / no_retry / unknown` 分类；可重试履约保留 `PENDING`，其他失败标为 `FAILED`；补偿只扫描 `PENDING` | 未引入上述分类；履约失败返回 false，补偿扫描 `PENDING / FAILED`                         |
| 网站购买实现         | 单一 `website/`，共用 OrderCheckout，默认优先 PayPal                                                                            | 主站使用 `website-shared`；`website-tgd-pro` 独立实现同一支付协议，两处均默认优先 Clink |

两边的 Clink 自动续费都跳过 recurring `order.succeeded` 的权益发放，只由 Invoice 路径履约；这部分没有首期双事件同时发放的设计差异。两边的本地订单取消也都不等于关闭远端支付入口，Stripe 不能把退出收银台直接当成渠道已取消付款。

## 订阅模型与用户行为

| 项目         | gmap                                                                                                 | extension-tg-download                                                                                                               |
| ------------ | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 隔离维度     | `(user_id, product_kind)`：Maps 插件、Online、API，三线可并存                                        | `(user_id, subscription_type)`：插件 `10`、App `20`，两类可并存                                                                     |
| 商品与权益   | 同线多档，`tier_rank` 判档次，`display_order` 只管展示；权益以月额度为主                             | 以下载权益、每日额度和速率为主；普通商品使用展示排序，App 另按周期硬编码升级顺序                                                    |
| 周期         | `none / month / quarter / year`                                                                      | 另有 `lifetime`，按 2400 个自然月表达终生；年卡解析保留，插件发布基线售月、季、终生                                                 |
| 实例保存内容 | 保存商品、续费方式、渠道、协议与客户引用、起止时间；周期从商品读，价格与首单事实由订单及渠道引用提供 | 另存 `product_price_id / period / original_order_no / cancelled_at`；保留旧实例空字段回退                                           |
| 有效期内购买 | 普通同线购买被拒绝；更高档走独立升级接口                                                             | 插件普通重复购买被拒绝；App `_is_app_upgrade` 放行月 → 季 → 终生的更高周期商品                                                      |
| 单次升级     | 同线月付升更高档，按剩余账期折算差价，支付后只换档、到期日不变；PayPal / Clink 已提供能力            | App 仍走普通下单，按目标商品全价收款；一次性履约从现有有效期继续增加新周期，没有差额报价与抵扣                                      |
| 自动续费升级 | 有报价、确认、统一结果及事件同步链；Clink 立即折算换价，PayPal 自动续费升级关闭                      | 没有通用 preview / confirm / plan-state 能力，也没有同类升级接口                                                                    |
| 升级后的续费 | 首购才能写商品档位；后续付款只推进账期，避免恢复为首购旧档                                           | 账期向后推进时按付款订单快照更新商品、价格行与周期                                                                                  |
| 终生特殊处理 | 没有终生商品路径                                                                                     | 有效终生权益不被后到账有限周期订单覆盖；App 买终生后另有停止 Google Play 自动续费入口                                               |
| 管理入口     | Dashboard 按 `product_kind` 管理当前线；后端读取本人订阅引用                                         | 网站 Pricing 管理插件订阅，请求体为空；App / Play 另走对应客户端和渠道路径                                                          |
| 自动续费状态 | 有效期 + 实例 `auto_renew`，不保存本站取消状态                                                       | 还参考 `cancelled_at`，状态接口提供取消标志；现役源码只见保留或清空该字段，未发现写入取消时间的路径，不能据此认为已实现实时取消同步 |
| 好评赠送     | API 配置固定关闭，claim 直接拒绝                                                                     | 活动开关、IP 可见性、领取与 TG 身份绑定路径仍在                                                                                     |

共同账期规则：一次性购买按业务时区增加自然月；自动续费采信 Provider 给出的已付到期时间，只向后推进。商品模式与周期在下单时校验并冻结，配置变更不应改写已创建订单的履约事实。

TG 的订阅技术文档仍写“不提供升级”，但 App 下单源码已存在上述更高周期购买例外。这里按实际可达入口区分该例外与 gmap 的折算升级。

## 对 Stripe 接入的影响

1. 以 gmap 现有多档位和两种升级链路为基线，同时覆盖单次购买、订阅首期、自动续费、单次补差及自动续费协议内升级。无需移植 TG 的 App 类型、终生商品、Google Play 或旧字段回退。
2. 复用现有网站升级接口与 `SubscriptionUpdateResult`；Stripe 的金额预览、付款后换档、待用户动作和事件收敛需要按其官方协议补齐。当前 `price_snapshot_id` 对应 Clink 的报价快照，能否直接承载 Stripe 预览结果仍需核实，不能只凭接口名称认定可直接复用。
3. 升级折算付款与完整周期续费分别核对金额和服务区间；保留 gmap 的续费不覆盖已升级档位规则。Stripe 不能采用 TG“续费金额必须等于首单”的规则来处理升级发票。
4. gmap 商品播种会停用全部非 PayPal 渠道价，接入 Stripe 必须同步调整。商品模式是商品级字段，也意味着切换为自动续费会影响该商品在各渠道的可售资格，不能理解为给 Stripe 单独切一个模式。
