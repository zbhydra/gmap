# 001 · 取消自动续费 - 后端数据与接口

> 状态:暂缓实现。本文仅保留后续方案,当前不得按本 plan 开工。

## 目标

后续让已购买 Unlimited 的用户在站内停止下一次自动扣款,当前周期权益保留到 `expires_at`。

## 依赖 plan

无。`002.取消自动续费-Pricing前端与验证.md` 依赖本 plan 的接口和响应字段。

## 已确认口径

- 取消只停止下次扣款。
- 不退款、不立即降级、不缩短 `expires_at`。
- 已取消续费但尚未到期时不能再次购买;到期后可重新购买。
- 到期前恢复自动续费不做。
- 不能从当前商品配置判断订阅实例的购买方式;只保存计费模式、渠道取消句柄和最近一次确认取消时间。
- 用户在支付平台后台取消时,本站可能收不到通知;站内取消接口需要能把渠道“已取消”结果同步回本地。
- 本站不维护渠道实时自动续费状态;`cancelled_at` 为空不保证渠道仍会扣款。

## 方案取舍

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 只跳转用户去 PayPal/Telegram 自行取消 | 不选 | 实现最轻,但站内状态无法确认,用户体验差 |
| 站内调用渠道取消,本地只存最少渠道引用 | 选中 | 满足用户目标,不引入账单中心和金融级流水 |
| 新建完整 billing subscription 表和事件表 | 不选 | 过度设计;当前只有一个 Unlimited 月订阅 |

## 外部事实

- PayPal 使用 Subscriptions API cancel: `POST /v1/billing/subscriptions/{id}/cancel`。
  来源: https://developer.paypal.com/docs/api/subscriptions/v1/#subscriptions_cancel
- Telegram Stars 使用 Bot API `editUserStarSubscription`,传 `user_id`、`telegram_payment_charge_id`、`is_canceled=true`。
  来源: https://core.telegram.org/bots/api#edituserstarsubscription
- Bot API 只称 `telegram_payment_charge_id` 为订阅的支付标识,没有说明自动续费后应传首期、最新一期或任意一期 ID;公开资料没有足以确认该行为的真实请求响应。
- Telegram Test DC 的 Bot API 路径为 `/bot<TOKEN>/test/<METHOD>`,订阅周期可用 60 秒。正式实现前按 `@../../004.订单系统/tech-支付与履约.md` 第 11.4 节完成两条订阅的首期 ID / 最新 ID A/B 取消实验。

## 后端设计

`user_subscriptions` 新增 nullable 字段:

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `payment_method` | String(32) | 当前订阅渠道 |
| `channel_subscription_id` | String(256) | PayPal subscription id 或经 Test DC 实测确认期次的 Telegram charge id |
| `channel_uid` | String(64) | Telegram 付款用户 ID;PayPal 可为空 |
| `billing_mode` | String(16) | 订阅实例计费模式快照;当前为 `auto_renew`,不随商品配置变化 |
| `cancelled_at` | BigInteger nullable | 本站最近一次确认渠道取消成功或已经取消的时间,毫秒;最近一次订阅付款成功后清空 |

接口里的 `auto_renew` 由 `expires_at > now && billing_mode="auto_renew" && cancelled_at is null` 计算,不得从当前商品 metadata 推断。`cancel_at_period_end` 由 `expires_at > now && billing_mode="auto_renew" && cancelled_at is not null` 计算。`cancel_available` 在 `auto_renew=true` 的基础上再要求渠道订阅引用完整。这些字段只表达本站最后一次已知状态,不是渠道实时查询结果。

接口:

```text
POST /api/client/subscription/cancel-auto-renew
```

流程:

1. 登录用户读取当前 `user_subscriptions`。
2. 无未过期 Unlimited 返回 `INVALID_REQUEST`,data.reason=`no_active_subscription`。
3. `cancelled_at` 不为空时幂等返回当前订阅状态。
4. 缺少渠道引用返回 `INVALID_REQUEST`,data.reason=`cancel_not_available`。
5. `paypal`: 调 PayPal cancel。
6. `telegram_stars`: 调 Telegram `editUserStarSubscription`。
7. 渠道成功或明确返回已经取消 / 非自动续费状态时,更新 `cancelled_at=now`。
8. 返回当前订阅状态。

履约补充:

- 首期订阅履约写入 `payment_method/channel_uid/billing_mode`,并清空 `cancelled_at`;Telegram 的 `channel_subscription_id` 写入时机以 Test DC 实测结论为准。
- 每一笔订阅付款成功都清空 `cancelled_at`;Telegram 以 `is_recurring=true` 为准,首期和后续续费执行相同状态更新。
- 历史有效订阅尽量从最近成功订单回填;缺失渠道引用时不猜测商品配置,允许用户走渠道侧或支持处理。

## 验收标准

当前不执行验收。恢复实现时按以下标准验收:

## 风险与回滚

- 暂缓期间用户仍需到 PayPal / Telegram Stars 等支付渠道侧取消自动续费。
- 渠道取消成功但本地更新失败:用户不会再被扣款,本地仍可能显示可续费;用户可重试或人工修正。
- 本地更新成功但渠道调用失败必须禁止发生;实现顺序固定为先渠道成功再写本地。
- 回滚接口时保留新增 nullable 字段不影响旧逻辑;需要恢复续费只能让用户到期后重新购买。
