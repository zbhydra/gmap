## #1 配置存储 —— 调研结论

**功能配置 100% 存客户端(chrome.storage.local),无 storage.sync,无远程拉取。**

本地 key 全集(已扫全部 `storage.set` 调用点):`request_interval`、`auto_download`、`fields`、`export_data_format`、`stuck_max_retry`、`license`(key 本体)、`google_drive` / `hubspot`(OAuth token)、`spotify` / `g_token`(作者其他项目残留)。清浏览器数据即归默认(默认值由 `onInstalled` 写入)。

**唯一的远程配置通道**(容易被误认为"远程配置"):`GET_IS_PRO` → 云函数 `isPro` 返回的 `opts`,含:
- `plan`(套餐名)与配额——服务端是真源
- `extension.content.html`——**服务端下发的 HTML 片段,直接 innerHTML 注入面板**,作者免发版改公告/广告
- `extension.version.v`——远端版本号,用于"有新版本"提示

这三个每次 boot 现拉、只进内存(`planOpts`),**不落盘**。本质是"运营性远程配置",不是用户功能配置。

## #4 下标漂移对策 —— 已拍板(2026-08-29)

### 参考实现(tg-download)的机制,已调研核实

五要素:

1. **编译期完整默认值**:包内 `DEFAULT_*_CONFIG` 常量(带 index signature,允许服务端下发客户端不认识的键),类型定义与默认值同文件
2. **每生命周期一次拉取**:content script 初始化时 `loadPromise ??= fetch()` Promise 记忆化,每 document 至多一次 HTTP GET;SPA 内路由切换不重拉,刷新/新开 tab 才拉
3. **background RPC 透传**:content → background → `GET {__API_BASE_URL__}/api/client/tg/config`,响应信封 `{code: 10000, data, msg}` 拦截器剥壳;`requireAuth: false, skipRetry: true, skipErrorToast: true`;响应体上限 16KB
4. **Object.assign 浅覆盖到模块级单例**:`const config = {...DEFAULT}` 拷贝不共享引用 → `Object.assign(config.dom, remote.dom)` 分组覆盖;远程缺键保留本地值、多余键原样进入、同名键**不做任何校验**(契约写在文件头注释)
5. **try/catch 静默回退**:拉取/解析失败仅 logger.error,返回包内默认值,绝不中断功能

参考实现刻意没有的东西(与用户"看时间去拉"的表述的差异,实现时定):无 storage 缓存、无时间间隔阈值、无版本协商——频控仅靠每 document 记忆化。**按用户拍板:拉取时机按时间控制**(如 storage 存时间戳 + 间隔阈值,如 1 小时内不重复拉;间隔内直接用上次结果,无上次则用包内默认)。参考实现"远程改配置刷新页面才生效"的热更新机制保留:消费者每次运行时现读活对象,覆盖发生在扫描器启动前即可。

## #3 DOM 选择器改版 —— 已拍板(2026-08-29)

实测背景:原插件的 `#searchboxinput` 已不存在(现为 `div[role=search] input#ucc-1[name=q]`),导致它点 Start 静默失败。

三个子决策:

### 3.1 关键词来源:不读 DOM ✅

黄金样本证实:响应剥壳后 `arr[0]` 第一个字符串就是查询词;URL(`/maps/search/<kw>/@…`)兜底。搜索框 DOM 完全不碰。

### 3.2 翻页机制:DOM 滚动为主,纯协议翻页为待办 ✅(实测结论)

实测发现新 Maps 是**预取模式**:初始响应含 20 条,滚动只消费本地数据(7→14→21 条零请求),耗尽后才拉下一批。翻页请求的 cursor 定位在 pb 的会话序号段:

```
1s{会话ID}:2        → 第二批变为 :135
2s1i:0,t:11886,p:{会话ID}:2  → t:246204,p:...:135
17s{会话ID}:33      → :136
```

但**这些新值在上一批响应中不存在明文**(实测 `SID:N` 模式零命中),由前端内部状态生成——纯协议翻页需继续逆向 continuation 生成规则,列为待办实验。DOM 滚动方案(语义 role 选择器 `div[role=feed]` + scrollTop,远程配置可下发)经实测有效,作为主方案,与插件行为一致。

### 3.3 失败不静默(设计原则)✅

原插件选择器找不到即静默 return(本次实测踩坑)。复刻原则:选择器查询、响应解析、schema 缺失一律要可见——UI 状态提示 + 错误上报,禁止静默吞错。

## #5 MV3 SW 生命周期 —— 已拍板(2026-08-29)

问题本质:MV3 service worker 空闲约 30 秒即被 Chrome 终止,唤醒后是全新进程——内存状态全丢、`setTimeout/setInterval` 不可靠。原插件把批量任务队列与每个关键词的 try/stuck/complete 计数全放 SW 内存(mod_137),靠两条补丁续命:contentScript 定期 `KEEP_LIVE` 喂活性 + 每 15 秒轮换提取 tab 激活。致命场景:用户关掉所有 Maps 页 → 心跳停 → SW 死 → 任务队列蒸发,无恢复。

复刻决策:**状态落盘的步进状态机,不对抗平台模型**。

| 职责 | 位置 |
| --- | --- |
| 采集主循环(滚动/解析/去重/导出) | contentScript(页面进程,天然长命;原插件此处架构正确,照搬) |
| 批量任务队列 | chrome.storage.session / IndexedDB 持久化 |
| 批量调度 | 步进式:每完成一步写状态;SW 被任意事件唤醒 → 读状态 → 推进一步 → 写状态。SW 随时死都无影响 |
| 兜底恢复 | chrome.alarms(30 秒级)扫描未完成任务队列,页面全关后仍能恢复/收尾 |
| SW 本体 | 轻量化为 tab/window API 的无状态代理,不持有任何必须存活的业务状态 |

不采用的方案:KEEP_LIVE 心跳续命(与平台对抗,Chrome 收紧策略即失效);offscreen document 常驻 worker(hack,商店审核风险)。原插件的 15 秒 tab 轮换保留与否由实测决定——它同时服务于"防后台 tab 节流"(提升采集页面计时器精度),与 SW 保活无关,若实测需要则以 alarms/消息驱动方式实现。
