# 08 · 反混淆处理说明(对文件做了什么)

## 处理原则

用户授权破坏性处理(原始 zip `G-MAPS-EXTRACTOR-v2.5.1.zip` 留档于 scratch 目录)。原始 `src/` **未动**,处理产物全部落在 `readable/` 与本文档目录;原 `readable/`(仅 prettier 格式化的中间产物)已被覆盖——它没有反混淆,阅读价值为零。

## 处理流水线

1. **webcrack**(npm,基于 babel):
   - 还原 obfuscator.io 混淆:字符串数组解码(所有 `_0x4c1c(0x52e)` 查表调用 → 明文字符串内联)、常量折叠、控制流还原、dead code 清理
   - unminify:webpack runtime 结构还原、格式化
   - 效果:字符串 100% 明文;变量名仍为 `_0x` 风格(未 mangle,保留符号稳定性);控制流已顺序化
2. **webpack 模块拆分**(自写脚本,`@babel/parser` 定位数组式 bundle 的模块表,按 AST start/end 切片):
   - 8 个 bundle 共约 2700 个模块拆为独立 `mod_NNN.js`
   - 拆分产物在 `/tmp/gmap-deob/split/<bundle>/`(临时目录;复现命令见下)
3. **辅助文件格式化**:manifest.json(JSON.stringify 2 空格)、6 个 html/css(js-beautify)
4. **核心业务模块提炼** → `readable/modules/`(见 roadmap 索引表,共 11 个文件)

## 复现命令(从原始 zip 开始)

```bash
# 1. 解压
unzip G-MAPS-EXTRACTOR-v2.5.1.zip -d gme-src

# 2. 反混淆(webcrack)
mkdir /tmp/gmap-deob && cd /tmp/gmap-deob && npm i webcrack
cat > deob.mjs << 'EOF'
import { webcrack } from 'webcrack';
import { readFileSync, writeFileSync, mkdirSync } from 'fs';
import { dirname, basename } from 'path';
const [,, input, outDir] = process.argv;
const name = basename(input, '.js');
const result = await webcrack(readFileSync(input, 'utf8'), {
  jsx: false, unminify: true, unminifyRetry: false, mangle: false, deobfuscate: true,
});
mkdirSync(`${outDir}/${name}`, { recursive: true });
writeFileSync(`${outDir}/${name}/index.js`, result.code);
console.error(`[${name}] done (${result.code.length})`);
EOF
for f in service-worker background contentScript rsScript injected popup dashboard options; do
  node deob.mjs "gme-src/src/$f.js" out
done

# 3. webpack 模块拆分
cd /tmp/gmap-deob && npm i @babel/parser @babel/generator
cat > split.mjs << 'EOF'
import { parse } from '@babel/parser';
import { readFileSync, writeFileSync, mkdirSync } from 'fs';
const [,, input, outDir] = process.argv;
const code = readFileSync(input, 'utf8');
const ast = parse(code, { sourceType: 'script', allowReturnOutsideFunction: true });
let found = null;
for (const node of ast.program.body) {
  if (node.type === 'ExpressionStatement' && node.expression.type === 'CallExpression') {
    const arr = node.expression.arguments.find(a => a.type === 'ArrayExpression');
    if (arr) { found = arr; break; }
  }
}
if (!found) { console.error('NO MODULE ARRAY'); process.exit(1); }
mkdirSync(outDir, { recursive: true });
found.elements.forEach((el, i) => {
  if (!el) return;
  writeFileSync(`${outDir}/mod_${String(i).padStart(2, '0')}.js`,
    `// ===== module ${i} =====\n` + code.slice(el.start, el.end) + '\n');
});
console.error(`${found.elements.length} modules -> ${outDir}`);
EOF
for f in background contentScript rsScript injected popup dashboard; do
  node split.mjs "out/$f/index.js" "split/$f"
done
# options.js / service-worker.js 是对象式 bundle({key: fn}),数组脚本不适用,
# 前者可用同思路找 ObjectExpression properties,后者直接读即可(仅 3KB runtime)。
```

## 阅读反混淆代码的注意事项

- 变量名 `_0x...` 无语义,读的时候靠**字符串常量和方法 key**(`key: "generatePin"` 这类是明文)定位逻辑
- babel 编译的 async 函数呈 regenerator 状态机(`case 0/2/…` + `abrupt("return")`),按顺序读 switch 即为原 await 序列
- class 定义呈 `_236fd2 = class; _2087cf = [{key, value}…]` + defineProperty 循环,`_2087cf` 数组就是方法表
- 大量 `![]`(false)、`!![]`(true)已由 webcrack 还原;剩余 `0x` 十六进制数字直接按十进制读
- jQuery `$` 全局来自 content_scripts 注入的 jquery-3.2.1;`Parse` 全局来自 service-worker/dashboard 加载的 parse.min.js
- 混淆前的源码是 TypeScript(Vue SFC + webpack + babel 的编译产物特征明显),若做深度对照可按模块边界猜测原目录结构(mod_347 ≈ dashboard 的主组件)
