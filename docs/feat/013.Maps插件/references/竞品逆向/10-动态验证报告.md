# 10 · 动态验证报告(Playwright 实测)

> 2026-08-29 实测。工具:Playwright(launchPersistentContext + Chromium for Testing 151)。
> 测试脚本存于 `/tmp/pw-gmap-test/`(临时),黄金样本已归档至本目录 `golden-samples/`。

## 测试方法

1. `--load-extension` 加载原插件(未打包目录)+ 全新 profile(无 Google 登录态)
2. 打开 Google Maps 搜索 `coffee in manhattan`,CDP 网络层捕获全部响应
3. 分别采集「直接导航搜索 URL」与「SPA 内搜索」两种模式的 `/search?tbm=map` 响应
4. 按 `04-数据字段字典` 的下标表写解析脚本,对真实响应逐字段验证

## 结论一:数据协议未变,04 文档下标 100% 有效 ✅

两种响应形态都抓到并解析成功,**20 个商家全量命中**:

| 字段 | 命中 | 字段 | 命中 | 字段 | 命中 |
| --- | --- | --- | --- | --- | --- |
| name | 20/20 | rating | 20/20 | place_id | 20/20 |
| address | 20/20 | reviews | 20/20 | kgmid | 20/20 |
| categories | 20/20 | lat/long | 20/20 | fid | 20/20 |
| timezone | 20/20 | street/municipality | 20/20 | owner | 20/20 |
| website/domain | 18/20 | phone | 11~14/20 | price | 19/20 |

低命中均为数据本身缺失(咖啡店无电话/酒店星级),非解析失败;`plus_code` 在列表响应中不存在——印证插件设计(Plus Code 由其服务端按经纬度补全)。

列表定位:`data[data.length - 8]`(顶层长 72 → `arr[64]`)依然精确;详情节点在 `arr[64][i][1]`(插件 V2 分支的 `item[1]`,数组 typeof 也是 object,走 V2 分支正确)。

## 结论二:两种响应格式并存,插件的剥壳逻辑仍工作 ✅

| 形态 | 触发方式 | 结构 |
| --- | --- | --- |
| **格式 A** | 直接导航 `google.com/maps/search/<kw>`(页面数据请求) | `)]}'\n` + 纯数组,**无尾哨兵** |
| **格式 B** | SPA 内搜索/滚动加载的 XHR | `{"c":0,"d":")]}'\n[...]"}` + 尾部 `\n/*""*/` |

格式 B 与 v2.5.1 `toJson` 逐字吻合:`slice(0,-6)`(去 `\n/*""*/`)→ `JSON.parse().d` → `substr(4)`(去 `)]}'`)→ `JSON.parse`。
格式 A 插件**没有**适配(`slice(0,-6)` 会破坏格式 A 的 JSON)——但格式 A 只在直接导航时出现,插件运行场景(SPA)只产生格式 B,故不影响插件;**复刻时两种都要处理**。

样本:`golden-samples/format-A-direct-nav-20places.txt`(678KB)、`format-B-spa-xhr-20places.txt`(755KB,`{"c":0` 实证)。

## 结论三:插件当前的实际状态——协议活着,壳有裂缝 ⚠️

实测发现 v2.5.1 两个失效点(均为 DOM 层,非数据层):

1. **强制登录**:全新 profile 无 Google 登录态 → `GET_IS_PRO` 返回 `user:null` → `initUI()` 不执行 → **面板(#map_scraper)完全不出现**。插件硬依赖登录,免费也必须登。
2. **搜索框选择器失效**:`#searchboxinput` 已改为 `div[role=search] input#ucc-1[name=q]` → `start()` 里 `inputKw.length < 1 → return`,即使登录了,点击 Start Extracting 也会直接返回(不采集、无报错)。本次未能验证到面板挂载(登录阻塞),此点由代码逻辑推断,置信度高。

复刻启示:**不要照抄它的 DOM 选择器**,要么动态探测(`div[role=search] input` / `div[role=feed]` 这类语义 role 尚稳定),要么干脆不依赖 DOM(直接构造搜索 URL + 拦截响应,见结论四)。

## 结论四:复刻的最小采集方案(实测可行)

不注入扩展、不滚动,直接:

```
GET https://www.google.com/search?tbm=map&authuser=0&hl=en&gl=us
    &q={关键词}
    &pb=!1s{关键词}!7i20!10b1!12m58!...(可从直接导航搜索页时自己抓一份完整 pb 模板)
```

- 拿到格式 A 响应,`slice(4)` 后 JSON.parse,`arr[len-8]` 取列表,下标解析
- 样本中的 pb 参数含 `!7i20`(每页 20 条);翻页/继续加载用 pb 内的分页段(或直接改 q 重查)
- 请求头需要常规浏览器 UA + `hl/gl` 一致性;未登录可访问(本次实测未登录成功拿到数据)
- 这是服务端直连方案,比插件"浏览器内拦截"更适合服务端化;注意频控(每次间隔建议 ≥ 插件的 5-10 秒档位)

## 附:测试环境注意事项

- 必须加 `--disable-quic`:本机直连 Google 时 QUIC(UDP)不稳定会导致 Chromium 导航超时(本次首个坑,curl 可达但 Chromium 挂)
- Playwright 网络层事件(`page.on('response')`)能覆盖页面级请求;页面主世界 hook XHR 对 Maps **无效**(前端闭包缓存了原生 XHR 方法引用,晚注入拦不到)——验证采集协议一律用 CDP 层
- `resp.text()` 会拖慢大响应消费,过滤静态资源要在读 body 之前做
- Google 登录无法(也不应)自动化;需要登录态的插件功能验证,用 hydra 自己的 Chrome profile 目录作为 `userDataDir` 启动即可
