## 2. 已确认问题与当前修订

### 发布阶段的用量入账重试不能占住全局执行名额

Codex 针对原冻结方案提出，主助手已沿源码复核；同一 reviewer 已定向复验当前替代方案，原 P1 关闭。

业务位置是“采集结束 → 生成并上传 CSV → 登记本次消耗的 Online records → 标记任务完成”。这里的计量是套餐用量入账，不是支付扣款；重试用量入账与完成状态提交，不重新采集。

- 原冻结设计 §4.2 要求 PUBLISHING 中按原间隔持续重试计量与终态提交。
- CAS `runtime/export_job_runtime.py` 的 `_dispatch` 先取得 `_slots`；`_run` 在执行、发布全过程持有名额，直到 `finally` 才释放。
- 本仓 `MapsOnlineTaskService.complete_task` 是普通异常后每五秒重试；`usage_service.consume` 还会读取当前套餐配置，故障不必影响整个数据库，可以只影响一类账号。
- 持续失败的任务占满名额后，其他账号的新采集也无法推进。这是将两个现有机制组合后产生的问题。

没有证据表明结算一定持续失败；问题是原实现未设重试上限，持续异常时会一直占用名额。用户选择接受任务局部失败，当前设计 §4.2 改为发布异常记录日志、尝试一次失败收口并释放名额，不再延时重试。用量、成功终态与下载引用同一短事务提交，取消分步提交所需的 `uploaded_at`；提交响应丢失时依靠原终态条件更新，保留已提交的成功事实。数据库不可用时允许失败状态暂未写入，重启遗留 PUBLISHING 只收口失败，不重新上传或结算。

ccmp定向复验发现Run字段仍残留“上传完成事实”、任意唤醒入口的PUBLISHING行为需明确，已删除残留并统一为再次调度时只失败收口；同一reviewer复验通过。沿CAS先条件更新Run、未命中不写流水、同session统一提交的顺序已写明。数据库故障导致Processing滞留是当前接受的代价，不采纳新增巡检或GET修复副作用；缺少实际挂死证据的额外超时机制不纳入本次。

### 原调用查询与启动风险的当前替代方案

用户指定的CAS `docs/feat/023.官网社媒导出/plans/2026-10-20-gmap-collector-async.md` 已完整读取。它定义目标异步协议，当前主线源码尚未实现这些接口；先前“当前Collector仅同步等待、stats不能取结果”的源码结论仍成立，当前方案已采用新的目标合同。

源异步计划要求提交前保存task_id与原Collector地址，Server重启后查询原调用；搜索404按item失败、可选补全404保留基础行，不默认重采。Collector首次受理后执行期限固定，临时结果满一小时定期回收，Collector重启允许丢失索引并返回404。按该边界更新本项目设计§3.2/3.3与007，不将原同步代码或上游计划审查视为异步运行证据。

本项目有两项针对用户既有事故经历的必要适配：

- 复用Run首次持久化started_at计算采集与查询总期限，Server重启不刷新；不沿用源计划§4.4允许Server恢复后重新建立等待预算的建议。
- 发现与恢复入队在Runtime后台执行，不在FastAPI启动中等待恢复队列腾空。原源码 `start → discover_runtime_runs → enqueue(wait_for_space=True)` 被lifespan等待的路径需要替换。

此前建议取消全部采集恢复已由原调用查询方案替代；保留必要的本地CSV检查点、恢复截断与去重重建，已提交item跳过。两位reviewer之前只复验了本地发布收尾。本轮原方案reviewer已重新独立审查本次异步接入及两项适配，确认阻塞0；实施后的真实Server/Collector重启验收仍必需。用户上次事故未取得日志或复现，不认定其具体根因。

### 软额度被采集目标放大

本地无预留、运行中可超额是现有合同。新方案采用最多50个逻辑采样与源默认每项200条目标，允许一个地图Job配置10,000条目标，而Free月额度为1,000；实际是否取得这些行未验证。任务完成扣量前还能创建其他Job，故该月额度是准入软限制，不能描述成严格交付上限。

是否继续接受这种语义，或改为账号在途限制/固定交付预算，属于业务取舍；竞品公开页不能证明其允许或禁止同类超额。不能为了对标直接引入CAS积分预扣、复杂租约或另一套账本。
