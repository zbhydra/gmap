# 001 · Provider 采集基建

> 状态：已完成（2026-09-04）。稳定合同见 `@../tech-引擎Provider层.md`；抓取配方与实验事实见 `@../../../research/google-maps-scraping-方案调研.md` §12.30–§13。

## 目标

交付无持久状态的异步 Gmap Provider：HTTP Search、HTTP Reviews、gosom 单关键词 job 的提交与查询，以及对应后台配置。后续 Online 与 API 可分别调用，不需要本期预设任务系统或结果存储。

## 非目标

- 不新增任务 Model/service、分表、状态机、后台执行器、轮询循环或重启恢复。
- 不新增 OSS、结果文件、用户/额度、Online/API 业务路由。
- 不实现 Photos，不保留空方法或占位 DTO。
- 不增加统一 Provider ABC、自动路由器、Redis 队列或集群级并发控制。

## 依赖

1. 从生产服务器取回 `/data/gmaps-research/stress_test.py` 与调研 §12.35/§12.36 引用的 E12/E13 实验脚本，删除代理凭据、服务器地址和本地绝对路径后放入 `backend/tests/fixtures/gmap/`。
2. 复用已安装的 `curl-cffi`，不新增依赖。
3. 真实冒烟需要至少一条可用代理和一条可用 gosom API；缺少时按测试规范输出明确 skip 原因，不以 mock 冒充真实结果。

## 阶段一：证据与配置合同

### 改动

- 将脱敏实验脚本、必要原始响应和 29 列/Reviews 解析 golden 放入 `backend/tests/fixtures/gmap/`。
- 将 `gmap_engine` 从旧 `webshare` 对象统一为 `proxies: string[]`，删除旧格式兼容分支。
- 后台增加 Gmap Engine tab：HTTP/gosom 选择、代理多行输入、每进程并发预算。
- 收紧 gosom 配置：`base_url` 规范化后唯一；service 增加按 `base_url` 定向读取。

### 验收

- 仓库内能从脚本和原始响应追溯 pb 模板、停止条件、timeout、重试、`ll` 检测和 Reviews 位表。
- HTTP 模式至少一条代理；gosom 模式允许空列表；代理 URL 规范化、去空行、去重并保序。
- 日志和错误不出现代理用户名、密码或完整 URL。

## 阶段二：HTTP Provider

### 改动

- 建立 `provider/gmap` DTO、错误族、RPC client、请求模板、解析与条目合并；按技术合同固定字段类型、可空语义和多值顺序。
- 实现异步 `search_places`：一次调用一枚 NID，常规 pb 深分页，浏览器级 pb 补列，只对未覆盖 fid 请求 L2。
- 实现异步 `list_reviews`：四种排序、单页最多 60 条、返回 `next_cursor`。
- `http.py` 只导出模块级 `gmap_http_provider`；所有 Google 请求共享该实例的 `asyncio.Semaphore`，并发首次初始化由进程内 `asyncio.Lock` 串行化。每个请求随机选代理，重试优先换代理。

### 验收

- 29 列逐列符合调研 §12.30 golden；fid 合并不重复，不为星级分布增加 L2 请求。
- 常规分页使用 `!7i20!8i{offset}`、gzip 和证据脚本中的停止/重试参数。
- 主分页失败抛技术错误；浏览器 pb/L2 局部失败返回 `partial + warnings`。
- `ll` 注入两类 pb，软降级检测来自 E12 脚本，不新增猜测阈值。
- Reviews 两页 cursor 连续、无重复，排序和关键字段符合 E13 golden。

## 阶段三：gosom Provider

### 改动

- 实现异步 `submit_job`，按权重选择 gosom 实例并返回 `job_id + base_url`。
- 实现异步 `get_job`，按 handle 的 `base_url` 定向查询并映射状态、结果与错误。
- 将 gosom Entry 映射为统一 29 列；上游未提供字段保持空值。

### 验收

- 提交请求使用 `X-API-Key`，只包含一个关键词，成功接收上游 `202 + job_id`。
- 查询不重新随机选择实例；completed 时映射完整 `results`，非完成态不伪造 entries。
- 上游状态严格归一为 `pending / running / completed / failed`，终态与 entries/error 可空语义符合技术合同。
- Provider 内没有循环轮询、上游删除、任务持久化或 worker 管理。

阶段二与阶段三在阶段一的 DTO 与配置合同完成后可以并行。
