# 029. Telegram A Worker 等待与本地立即取消

> 状态：已完成（2026-08-27）。本文替换 Plan 024/025 中“活动传输确认停止后才移除任务并推进 FIFO”的旧取消合同。

## 1. 背景与证据

真实 Telegram A 固定频道已经证明两个相互关联的问题：

1. A message/WebPage Document 在 Worker 尚未被扩展捕获时点击，`prepareAMediaResource` 立即抛出 `stage=worker-selection`，而 Telegram 原生 document/audio 会保持 loading 并等待初始化或网络恢复。
2. 活动任务点击取消后可能长期停留在“取消中”。当前 `DownloadManager` 等待原 prepare/download Promise 结束才移除任务并继续 FIFO；A Worker `cancelProgress` 没有独立 ACK，网络断线、重连或长请求会让原 Promise 长时间 pending。

2026-08-27 真实运行证据：

- A26 WebPage PDF 首次点击出现 `GramJS Worker 尚未捕获`；稍后重复点击可以完成。
- A19 OGG 在 `zws4.web.telegram.org` 1006 和 `/a/progressive/document...` 500 后仍保持原生 loading，网络恢复后同一真实 E2E 约 1.3 分钟完成。
- 实施中 A26 首次点击进一步证明 `broadcastLocalDbUpdateFull` 可在 3ms 内返回空全量镜像，而目标 Document 在网络恢复后通过后续 LocalDb 增量到达；空 full 不是“目标确定不存在”的证据。
- 开发构建已能打印 EventRpc handler 原始 Error，确认失败发生在 Worker selection，不是 RPC transport。

Telegram A 上游源码 `3cd724ed8ebf8e1c907ef75ffb4cdbdd1ed2dc0f` 给出直接合同：

- [`connector.ts#L82-L131`](https://github.com/Ajaxy/telegram-tt/blob/3cd724ed8ebf8e1c907ef75ffb4cdbdd1ed2dc0f/src/api/gramjs/worker/connector.ts#L82-L131)：`initApi` 成功后才置 ready 并排空 API 请求队列。
- [`connector.ts#L207-L217`](https://github.com/Ajaxy/telegram-tt/blob/3cd724ed8ebf8e1c907ef75ffb4cdbdd1ed2dc0f/src/api/gramjs/worker/connector.ts#L207-L217)：ready 前的原生 `callApi` 返回未决 Deferred，不立即失败。
- [`worker.ts#L55-L65`](https://github.com/Ajaxy/telegram-tt/blob/3cd724ed8ebf8e1c907ef75ffb4cdbdd1ed2dc0f/src/api/gramjs/worker/worker.ts#L55-L65)：Worker 完成 `initApi` 后按同一 message ID 返回成功 `methodResponse`。
- [`connector.ts#L254-L277`](https://github.com/Ajaxy/telegram-tt/blob/3cd724ed8ebf8e1c907ef75ffb4cdbdd1ed2dc0f/src/api/gramjs/worker/connector.ts#L254-L277) 与 [`worker.ts#L124-L130`](https://github.com/Ajaxy/telegram-tt/blob/3cd724ed8ebf8e1c907ef75ffb4cdbdd1ed2dc0f/src/api/gramjs/worker/worker.ts#L124-L130)：取消按 progress callback 对应的 message ID 发送 `cancelProgress`，只设置协作式取消标记，没有独立取消终态。

## 2. 目标

- A message/WebPage Document 首次点击时若 GramJS Worker 尚未 ready，任务保持下载中并等待；ready 后沿同一 prepare/LocalDb/download 路径继续，不要求用户重复点击。
- waiting、Worker ready、LocalDb refresh、额度请求和真实传输任一阶段，本地接受取消后立即删除任务、完成 completion 并继续下一 FIFO 项。
- 底层取消、旧 Promise 收敛和资源释放只作为后台 best-effort 工作，不构成本地删除条件。
- 旧任务的进度、最终响应和异常按 `taskId` 丢弃或消费；取消任务不记录下载成功、下载失败或额度不足埋点。
- 开发构建保留 EventRpc 原始 handler Error 与 stack，生产 EventRpc 响应继续保持固定错误边界。

## 3. 非目标

- 不调用 Telegram 私有 React action、DOM 点击或模块私有 `callApi`；只观察并复用当前 Worker 消息协议。
- 不增加固定 3 秒等待、自动重试、备用下载 URL、第二套队列、Port、后台恢复或持久状态。
- 不保证底层请求物理立即停止，不保证已取消请求与下一项绝不重叠。
- 不保证取消 RPC 未抵达 injected 时旧任务绝不落盘；该极端风险由用户明确接受。
- 不退款已经成功消耗的额度，不恢复已从本地队列删除的任务。
- 不修改 Telegram 官方源码、`extension-pro/`、后端或网站。

## 4. 已确认取舍

2026-08-27 用户明确选择队列可用性优先：

> 本地接受取消后立即删除；发送底层取消只是附带的 best-effort 操作，不构成删除条件。

因此：

- 业务 FIFO 同时只有一个活动任务；已取消任务的物理请求可在后台短暂收尾并与下一项重叠。
- 资源释放、Abort、`cancelProgress` 或临时文件删除失败只记录，不恢复任务、不阻塞下一项。
- `cancelling` 不再是用户可见或业务等待状态；本地取消是瞬时终态，不保留历史。
- `<a download>` 触发前仍检查取消；浏览器保存已经触发后没有可靠撤回句柄，按已完成处理。

本计划改写既有内存状态机语义，触发 `hydra-feat` 复杂度闸门；上述风险与代价已经由用户明确批准。实现只复用现有 `taskId`、FIFO、AbortController、EventRpc 与 Worker waiter，不新增 generation/session token 或持久状态。

## 5. 唯一方案

### 5.1 Worker ready

`WorkerInterceptor` 在现有 `window.Worker` 拦截入口维护一个可取消 ready waiter：

1. 观察到 Telegram 无 channel `initApi` 时，保存对应 Worker 与 init message ID，但尚不记 ready。
2. 收到同一 init message ID 的成功 `methodResponse` 后记 ready，并完成当前 ready waiters。
3. 若扩展初始化晚于 init 生命周期，观察到 Telegram 原生 `callMethod` 可直接证明该 Worker 已越过 init 门槛，同样记 ready。
4. 新 Worker 的 `initApi` 替换旧引用并重新进入未 ready；响应只按当前 init message ID 生效。
5. 只创建 Worker 不算 ready，不增加 ping、轮询或固定 sleep。

### 5.2 A prepare

`prepareAMediaResource` 请求增加现有 `taskId`：

```text
prepare(taskId, identity)
  -> 等待 Worker ready
  -> ready：查询当前镜像
  -> miss：执行既有 single-flight full refresh
  -> 重查 identity；0 个候选则等待后续 LocalDb 增量并继续重查
  -> 返回资源、空结果或 cancelled
```

- cache hit 也必须先证明 Worker ready，因为 prepare 返回的 mediaHash 下一阶段仍由同一 Worker 下载；不能重建 Plan 025 已删除的“解析成功、下载必败”裂缝。
- prepare 使用现有 24 小时长调用预算，避免 EventRpc 默认 30 秒先于合法 Worker 等待失败；用户取消是提前退出机制。
- `AMediaResourceService` 只为当前 prepare 保存短命 AbortController；`cancelDownloadMedia(taskId)` 同时尝试取消 prepare waiter或真实传输。
- 每个任务以自己的 signal 等待共享 LocalDb refresh；取消只让该任务退出，共享 refresh 可继续完成并补缓存。
- LocalDb refresh 自身沿用已验证的 single-flight 与 25 秒本地方法 deadline；本计划没有证据要求修改该本地快照边界。
- full refresh 返回空镜像后，message/WebPage prepare 用现有 LocalDb owner 的一次性更新 waiter 等待后续增量；不再次 refresh、不轮询、不固定 sleep。0 个候选继续等待，多个候选仍按歧义返回空结果。

### 5.3 本地立即取消

`DownloadManager.cancel(taskId)` 的同步业务顺序固定为：

```text
本地标记 task 已取消
  -> 停止该 task 的速度采样
  -> fire-and-observed 发送 cancelDownloadMedia
  -> 从队列删除
  -> resolve completion
  -> 发布一次快照
  -> 继续下一项
```

- 不等待 cancel RPC，不读取其 `accepted` 决定本地终态。
- 当前执行改为真实执行 Promise 与本地取消 Promise 竞速；取消胜出即释放 FIFO。
- 真实执行 Promise 必须保留 fulfillment/rejection observer；迟到 reject 不能成为未处理异常。
- 任务对象在旧 Promise 收敛前只作为闭包内取消标记存在，不进入第二个队列或用户快照。
- 旧执行迟到完成、失败或额度拒绝均不记录对应终态埋点；首次点击埋点保持现有行为。

### 5.4 injected best-effort 取消

- injected 收到 task ID 后先把匹配 control 标为 cancelled，再尝试后续操作，不能以 `cancelProgress` 返回值决定本地 control 是否取消。
- prepare 阶段 abort 当前 Worker ready/refresh 等待；共享 refresh 本身可继续。
- Blob/Segment 发出 AbortSignal；退出、writer 终止和临时文件删除由旧 Promise 后台收敛。
- A mediaHash 已取得扩展 Worker request ID 时，`WorkerInterceptor` 尽力发送 `cancelProgress`，随后立即清理该 request 的 waiter、`reqList` 和 24 小时 timer，并用本地取消错误结算原 Promise；不等待 `USER_CANCELED` 或其它 Worker 响应。迟到 callback/response 按已删除 request ID 丢弃。
- 没有 Worker request ID 时只保留 cancelled 标记，后续不得创建保存动作。
- 非 placeholder 的现成 A mediaHash 同样在 Worker 调用入口等待 ready，并复用当前 transfer control 的取消 signal；不能只修 prepare。
- 每个下载在创建 Blob/object URL 和触发 `<a download>` 前检查 control；cancelled 时直接结束。
- 新任务可以覆盖 injected 的当前活动 control；旧任务 finally 只清理自己的 control，不能删除新任务控制项。

### 5.5 迟到事件与 UI

- `downloadProgress` 已包含 `taskId + sourceId`；本地任务删除或下一项启动后，旧事件无法同时匹配当前活动任务，直接丢弃。
- 同一资源重新入队取得新 task ID，不增加 generation token。
- 快照状态收敛为 `waiting / downloading / failed`；删除 `cancelling` 分组、文案、图标状态和判断分支。
- 页面 Widget 与 Popup 在同一快照 revision 中立即移除取消任务，不显示取消中。

## 6. 接口合同

| 接口 | 调整后合同 |
| --- | --- |
| `prepareAMediaResource` | 请求 `{taskId, identity}`；响应 `{resource, cancelled}`；Worker 未 ready 时等待 |
| `cancelDownloadMedia` | 按 task ID 尽力取消 prepare 或真实传输；`accepted` 仅诊断，不是业务终态 |
| `downloadMedia` | 保持 task ID 与长调用；迟到响应由已取消任务 observer 消费 |
| `downloadProgress` | 保持 `taskId + sourceId`；只更新当前活动任务 |
| `cancelDownloadTask` | 找到本地可取消任务即返回 accepted；底层结果不改变响应 |

EventRpc 仍是页面可伪造的非可信边界，不新增权限。开发构建在固定 `SERVER_ERROR` 响应之外打印 handler 原始 Error；生产只输出分类和错误码，不能把可能包含 token/引用的任意异常对象返回页面。

## 8. 实施阶段

### 8.1 合同与本地取消

- 收敛任务状态类型，删除 `cancelling` 的生产分支、UI 和 i18n 文案。
- 为内部任务增加本地取消 Promise；现有 drain 与真实执行竞速，取消同步删除并推进。
- 观察旧执行 Promise，按 task ID 丢弃迟到结果和埋点。

验收：取消不等待任何 mock RPC/旧执行 Promise；下一项立即开始；旧 Promise 随后 reject 不产生 unhandled rejection 或成功/失败埋点。

### 8.2 Worker ready 与 injected 取消

- 在现有 Worker interceptor 中识别 init request/response 与晚注入 callMethod 证明。
- prepare 增加 task ID、长调用 timeout 与可取消 Worker/refresh 等待。
- `cancelDownloadMedia` 统一尽力取消 prepare 或 active transfer；所有 control 先本地 cancelled，再执行底层操作。
- 保存前检查 cancelled，旧 control 的 finally 不影响新任务。

验收：A26 首次点击不因 Worker 未捕获失败；取消 ready/refresh 等待后本地队列立即继续；Worker ready 后未取消任务完成原 PDF 下载。

### 8.3 UI、验证与文档收口

- 页面 Widget 与 Popup 删除取消中分组和状态，只消费更新后的唯一快照。
- 删除真实 E2E 的固定 3 秒点击延迟。
- 更新现有测试与文档；不新增平行测试文件。

验收：A/K 页面与 Popup 同步立即移除取消任务；后续任务无需等旧传输终态即可开始；真实 A26、A19 和 K 既有下载仍完成。

## 10. 验收标准

1. A Worker 尚未 ready 时点击 message/WebPage Document，任务保持下载中；不出现 `stage=worker-selection` 立即失败。
2. Worker ready 后沿现有 LocalDb prepare 和 mediaHash 下载完成，无第二路径或固定等待。
3. waiting、prepare、额度与真实传输阶段取消都在同一同步操作中从页面与 Popup 消失、resolve completion 并启动下一项。
4. cancel RPC、Abort、`cancelProgress`、旧 Promise 或资源清理失败不恢复任务、不阻塞 FIFO。
5. A mediaHash 取消发出后，扩展 Worker waiter、`reqList` 和 timer 立即清理；迟到进度和最终响应不更新当前任务，不触发取消任务的成功、失败或额度不足埋点，迟到 reject 被观察。
6. 正常收到 injected 取消时不触发旧任务浏览器保存；取消 RPC 未抵达导致旧任务继续或落盘属于已接受风险。
7. 不再存在用户可见 `cancelling` 状态、分组或文案；失败与人工重试行为不变。
8. A26 PDF、A19 OGG、A18 CSV、K24 photo、K26 PDF 和 A/K 相册既有真实下载合同不回归。

## 12. 已知风险

- 底层协作式取消不保证物理立即停止；新旧请求可短暂重叠。
- cancel RPC 未抵达 injected 时，旧任务可能继续并触发浏览器保存。
- Worker init 长期不完成时任务持续 loading，用户通过取消退出；不增加自动超时或重试。
- `<a download>` 已触发后无法可靠撤回，本计划不伪装为可取消。

这些风险均可由用户重新操作修正，不涉及资金、安全、权限或不可恢复数据；不增加额外防护。
