## 2. 唯一方案

### 2.1 路由不变

- A progressive、K stream 与 A/K DOM HTTPS 继续进入同一个 `SegmentDownloader`。
- A mediaHash 继续进入 Telegram A Worker。
- DOM Blob 继续进入 `BlobDownloader`。
- 不引入 A `/download/`、K `downloadToDisc`、`chrome.downloads`、第二套网络请求或失败回退。

### 2.2 SegmentDownloader 双 sink

Range 预检后只选择一次存储 sink：

```text
totalSize < 200 MiB
  -> memory

totalSize >= 200 MiB && OPFS supported
  -> OPFS

totalSize >= 200 MiB && OPFS unsupported
  -> memory
```

memory 与 OPFS 共用预检、分块、并发、重试、进度、取消和保存逻辑。已经分类为可重试的网络中断与 408 分块响应在当前页面的同一任务内按既有固定延迟由各 position 独立持续重试，不设次数耗尽；position 成功后才释放其并发槽位，整批全部成功后才开始下一批，已写入内容和累计进度保留。每批使用局部 AbortController，并通过 `AbortSignal.any` 组合用户任务信号；任一 non-retryable 或用户取消会中止同批 fetch/retry delay，等待全部 position 退出后重抛原错误并清理当前 sink，FIFO 才推进。OPFS 已选中后任何写入失败直接结束当前项，不再回退内存。

### 2.3 临时内容

- core `SegmentDownloader` 统一拥有站点无关的 `extension-downloads/`，不碰 Telegram 官方 `downloads/`。
- 失败或取消时关闭 writer 并删除当前文件。
- 成功文件交给浏览器后保留 120 秒，再由当前任务捕获的 OPFS sink 只删除自己的 entry；不监听浏览器下载完成，120 秒仍未落盘允许失败并由用户重试。
- 页面或浏览器在中途关闭后，下一次打开 Telegram 时异步尝试递归删除扩展目录。
- 页面提前关闭导致成功清理 timer 消失时，同样由下次初始化清理；timer 不持久化。清理失败只记录并等待下次初始化；不增加注册表、后台状态、下载完成桥接或跨 tab 协调。

7. 下载到 50% 后关闭浏览器；重新打开 Telegram 后确认扩展发起目录清理尝试并记录结果。

### 6.3 memory 降级

- 从开始选择 memory sink。
- 下载、进度、取消和最终文件保持现有行为。
- Renderer 内存允许随文件增长；该降级不通过大文件内存验收，但属于用户已接受行为。

## 7. 停止条件

出现以下任一情况时停止对应阶段并回报，不增加备用路径：

- 当前 Telegram origin 支持 OPFS，但 MAIN world 无法完成 createWritable、position write、close、getFile 或 File object URL 保存。
- OPFS 分块完成前仍保留随文件增长的 ArrayBuffer/Blob 引用。
- 除已批准的任务内 120 秒单 entry timer 外，为清理成功文件必须增加浏览器下载观察协议、持久注册表、后台状态或跨 tab 协调。
- A progressive 或 K stream 必须更换现有 URL/Range 路由才能写 OPFS。
- 元数据只能通过额外下载完整媒体或生成截图取得。

OPFS 不支持不是停止条件，按已确认合同从开始使用 memory sink。OPFS 已选中后的写入失败只使当前项失败。
