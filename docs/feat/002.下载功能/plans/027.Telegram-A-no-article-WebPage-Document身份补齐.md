# 027. Telegram A no-article WebPage Document 身份补齐

> 状态：待批准。依赖 026 已完成的 A WebPage identity/query/prepare 合同；批准后按本文执行，完成时回填验收记录。

## 背景

026 已支持 A WebPage Document：scanner 从可见 WebPage 提取规范化 URL，建立 `webPage` identity；injected 按 LocalDb `localRepairInfo.type === 'webPage'` 查询唯一 Document；FIFO 队首 prepare 后下载原文件。当前入口只在 `.WebPage.with-document` 内查找 `.WebPage-text .site-name[href]`。

2026-08-27 对固定频道当前真实 DOM 的只读核验得到两类形态：

| 消息 | URL | WebPage 形态 | identity link | 当前按钮 |
| --- | --- | --- | --- | --- |
| 15 | `https://t.me/wadesk2023` | photo + article | WebPage 根与消息正文均有同一 URL | 有 |
| 24 | `https://fxtwitter.com/aiandcloud/status/2092539148334960855` | photo + article | WebPage 根与消息正文均有同一 URL | 有 |
| 20 | `https://podcast-api.hydrai.cc/api/albums` | `without-media no-article with-document` | WebPage 根无 link；消息正文有唯一 URL | 无 |
| 26 | `https://samplelib.com/pdf/sample-scanned.pdf` | `without-media no-article with-document` | WebPage 根无 link；消息正文有唯一 URL | 无 |

上游 `WebPage.tsx` 仅在 `siteName/title/description` 任一存在时渲染 `.WebPage-text`；因此 `no-article with-document` 没有根内 canonical link。当前 scanner 在 URL 缺失时直接返回 null，消息 20/26 不建立 placeholder，也不会进入 026 已完成的 query/prepare 链。

## 目标

- 消息 20/26 这类 `no-article with-document` 从消息正文唯一 URL 建立 WebPage identity，下载原 Document。
- article 与 no-article WebPage 使用同一个“候选 URL 规范化、去重、唯一命中”入口。
- A WebPage photo/video 与主消息 Document 行为不变。

## 非目标

- 不修改 `ALocalDbServices`、`AMediaResourceService`、RPC、DownloadManager 或下载器；026 已提供完整内部链路。
- 不在消息包含多个不同 URL 时猜测哪个 URL 对应 WebPage。
- 不处理没有真实故障证据的 Poll、reply 或其它嵌套 Document。

## 方案

两个文件，只补齐 scanner 的 WebPage URL 输入：

1. `extension/src/sites/telegram/content/dom/TelegramDomConfig.ts`：保留既有 `aWebPageIdentityLinkSelector` 键，将其语义改为“消息媒体查找范围内的 WebPage identity 候选 link”，默认值同时覆盖：
   - article WebPage 的 `.WebPage.with-document .WebPage-text .site-name[href]`；
   - no-article WebPage 对应的 `.text-content a[data-entity-type="MessageEntityUrl"][href]`。
2. `extension/src/sites/telegram/content/scanner/AVersionScanner.ts` `createPendingDocumentResource`：确认 `.WebPage.with-document` 与其 `.Audio/.File` 后，从整个 `context.element` 收集上述 selector 命中的 href，复用 `MediaUtils.normalizeWebPageUrl` 规范化并去重。结果恰好一个时建立 `{kind: 'webPage', url}`；0 个或多个时返回 null，不猜主项。
3. WebPage Document root、thumbnail、placeholder、query-only 元数据合并和 FIFO prepare 保持 026 现状；不新增 fallback 或第二套解析路径。

行为矩阵：

| 消息形态 | 当前 | 方案后 |
| --- | --- | --- |
| article WebPage Document，根 link 与正文 URL 相同 | WebPage placeholder | 去重后仍为同一 WebPage placeholder |
| no-article WebPage Document，正文有唯一 URL | 无资源 | WebPage placeholder，点击 prepare 后下载原文件 |
| WebPage Document，候选中有多个不同 URL | 无资源 | 不猜主项，仍无资源 |
| WebPage photo/video | DOM photo/video 下载 | 不变 |
| 主消息 document/audio | message identity 下载 | 不变 |

## 验收标准

1. 固定消息 20 与 26 均生成 `telegram-a-mediahash` placeholder，identity kind 为 `webPage`，URL 分别等于消息正文规范化 URL。
2. 固定消息 26 点击下载后取得原 PDF：900109 字节、SHA-256 `f0ca428c3a03350088ca78aba9b24dee3bcbac23ecbfa07a0eac4260db09f04b`。
3. 消息 15/24 的 WebPage photo 下载入口不变；主消息 document/audio 继续沿用 message identity。

## 验证方式

- 把 `a-version-scanner.spec.ts` 既有 WebPage Document fixture 改为真实 `no-article + text-content unique URL + File` 结构；不新增同合同的平行 unit。
- `telegram-real-download.spec.ts` 增加消息 26 的一次真实下载与大小/SHA-256 校验；消息 20 不增加重复下载用例。
- 每条 Telegram 真实测试开始时先关闭遗留 Telegram 页面，再创建唯一 fresh owner Page，结束时关闭；任何时刻不同时打开 A/K 页面。
- 在 `extension/` 运行 `pnpm test:unit:run`、`pnpm check`、`pnpm build`，实际启动 `pnpm dev`，再运行目标真实 E2E。
