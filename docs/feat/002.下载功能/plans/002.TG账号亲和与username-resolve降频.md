# 002 · TG 账号亲和与 username resolve 降频执行计划

> 最新口径:TG 账号亲和字段归入 Provider 私有 `extra.tg_client_ref`,不作为公共一等 claim。公共层只签名透传 `extra`,只有 Telegram Provider 读取该字段。

## 1. 目标

降低 Telegram 公共链接解析/下载链路触发 `ResolveUsernameRequest` 的次数,缓解 `FloodWaitError: ... ResolveUsernameRequest`。

本轮只处理两类重复:

- 解析和下载分配到不同 TG client,导致下载阶段无法复用解析账号的 entity cache。
- 同一 TG client 内使用 `get_entity(username)` 每次强制 resolve username。

不做全局 username 数据库缓存、不做跨节点账号状态同步、不做复杂重试编排。

## 2. 核心设计

### 2.1 账号亲和标识

`_ManagedClientState` 新增 `client_ref` 字段,值直接在创建 state 时计算:

```python
hashlib.sha256((phone + "***SEC***").encode("utf-8")).hexdigest()
```

不新增 `_build_client_ref()` helper。`client_ref` 只用于跨 token 透传和账号池优先匹配,不是授权边界。固定后缀只用于避免 token 暴露裸手机号 hash。

### 2.2 解析到下载的透传

Telegram parse-v2 成功后,把本次实际使用的 `client_ref` 写入对应 resource 的内部 `extra.tg_client_ref`。公开 parse-v2 JSON 不返回该字段,也不写入 `resources[].extra`。

透传路径:

```text
parse_link 使用的 TG client
  -> parse 返回结果携带 client_ref
  -> Telegram Provider parse result 写入 resource.extra.tg_client_ref
  -> resource token claims.extra.tg_client_ref
  -> download-pre-v2 校验并签发 media_download token,原样透传 extra
  -> download-v2 claims.extra.tg_client_ref
  -> resolve_download_context(preferred_client_ref=...)
  -> TelegramManager 优先选择匹配 client_ref 的账号
```

`extra.tg_client_ref` 是亲和 hint。目标账号不存在、冷却、不可用、负载高于最低负载 1 个以上、lease 失败或激活失败时,回退原账号池调度,不让用户因为 hint 失效直接失败。

### 2.3 同账号内 username resolve 降频

`TelegramLinkClient._resolve_message()` 不再直接:

```python
chat = await client.get_entity(parsed_link.username)
```

改为:

```python
input_chat = await client.get_input_entity(parsed_link.username)
```

后续 `get_messages()`、`GetStoriesByIDRequest`、grouped message 收集都直接使用 `input_chat`。不再为了 `chat_title` / `chat_username` 展示字段调用 `get_entity()` 获取完整 chat entity。

`get_input_entity(username)` 优先使用 Telethon session cache;cache miss 时仍可能请求 Telegram 并触发 `ResolveUsernameRequest`。本轮目标是:

- 同一账号命中 cache 时不再重复 resolve username。
- 不再额外调用 `get_entity(input_chat)` 拉完整实体。
- 不为了前端当前未消费的 owner/title/channel 字段消耗 Telegram resolve 配额。

`map_message()` 不再依赖完整 chat entity,改为接收显式 chat 元数据:

- `chat_username = parsed_link.username`
- `chat_title = None`
- `chat_id` 从 `input_chat` 的 `channel_id` / `chat_id` / `user_id` best-effort 提取;提取不到时由 media parse 层按 canonical link hash 兜底生成 `post.content_id`。

### 3.1 TG 账号池

文件:`backend/src/app/provider/telegram_manager.py`

- `_ManagedClientState` 增加 `client_ref: str`。

## 5. 验收标准

- 同一 Telegram parse-v2 返回的可下载 resource,其 resource token 可解码出同一个 `extra.tg_client_ref`。
- 同一 Telegram parse-v2 公开响应 JSON 不包含 `tg_client_ref`。
- 对该 resource 执行 download-pre-v2 后,media download token 可解码出相同 `extra.tg_client_ref`。
- download-v2 Telegram proxy 下载时,账号池优先尝试该 `extra.tg_client_ref` 对应账号。
- preferred 账号不可用或负载过高时,下载不会因为亲和 hint 失败而直接失败,仍回退其他可用账号。
- `_resolve_message()` 不再对 username 路径调用 `get_entity()`。
- parse-v2 公开响应允许 `post.owner.title` 为空,下载 token 与资源选择不依赖该字段。
- 对同一 username 的 parse→download 序列,亲和命中同账号时 `ResolveUsernameRequest` 触发次数下降。
## 6. 发布与观测

发布顺序:

1. 发布 resource token / media download token 的 `extra` claims。
2. 发布账号池 `client_ref` 与 `preferred_client_ref` 调度。
3. 发布 Telegram Provider parse 写入 `resource.extra.tg_client_ref`。

观测字段:

- `tg_client_ref_present`:parse-v2 签发 resource token 的 `extra` 时是否拿到 client_ref。
- `preferred_client_ref_present`:download-v2 是否收到 token 内的 `extra.tg_client_ref`。
- `preferred_client_ref_hit`:账号池是否命中 preferred client。
- `preferred_client_ref_fallback_reason`:未命中原因,例如 `missing` / `not_found` / `cooldown` / `unavailable` / `activate_failed`。
- `resolve_username_request_count`:TelegramLinkClient 内部记录 `ResolveUsernameRequest` 触发次数,用于验证亲和命中后同一账号重复解析是否下降。

这些字段只进日志或内部指标,不返回前端。
字段名保留 `tg_client_ref_*` 前缀是为了观测连续性;语义已经改为读取 `extra.tg_client_ref`,不是 media token 一等 claim。

## 7. 风险与回滚

- `client_ref = sha256(phone + "***SEC***")` 避免暴露裸手机号 hash;该字段仍不是授权边界。
- 若未来调整固定后缀,亲和命中可能下降,下载仍按普通账号池调度回退。
- `extra.tg_client_ref` 存在于 JWT claims,客户端可解码看到;禁止把真实 `phone` 写入任何 token、公开响应或日志。
- 账号亲和收益以 parse/download 尽量落到同一节点为前提;跨节点时因为节点没有同一进程内账号状态,会退化为普通调度。
- 账号亲和只能减少同节点同账号重复 resolve,不能跨节点共享 Telethon entity cache。
- `get_input_entity()` cache miss 时仍会请求 Telegram,仍可能 FloodWait;收到 FloodWait 后继续按现有冷却处理。
- 不再获取完整 chat entity 后,公开响应里的 `post.owner.title` 可能为空;前端当前不消费该字段,下载 token 也不依赖它。
