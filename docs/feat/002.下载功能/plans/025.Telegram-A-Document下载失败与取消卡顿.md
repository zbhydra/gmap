# 025 · Telegram A Document 下载失败与取消卡顿

## 1. 文档目的

本文记录 Telegram Web A 版主消息 Document 下载的用户故障、源码排查结论、已实施修复、验收结果和剩余边界。

修复代码和自动验收已经完成；本文作为执行与验收记录保留，不代替长期技术合同。自然 cache miss、0 B 底层停滞阶段和取消耗时分布仍缺真实证据；稳定合同与实际变更仍需同步回 `@../tech-扩展端TG扫描.md` 和 `@../changelog.md`。

## 2. 用户遇到的问题

### 2.1 点击 Document 后解析失败

用户在 Telegram Web A 版下载同一个 Document 时，反复出现以下错误：

```text
[DownloadManager] Telegram A 主消息 Document 点击解析未返回真实参数:
responseCount=0,
matched=no,
documentId=missing,
mediaHash=invalid;
请重试
```

实际表现不是稳定失败：

1. 同一个资源首次点击可能失败。
2. 刷新网页数次后，同一个资源可能突然可以加入下载。
3. 再次刷新后，同一个资源又可能持续失败。
4. 失败涉及不同消息，不是单个 fixture 永久缺少 Document。

`responseCount=0` 是首要事实：MAIN world 查询没有返回与 `chatId + messageId` 匹配的 Document。`matched=no`、`documentId=missing` 和 `mediaHash=invalid` 都是空响应的后续结果，不是三个独立故障。

### 2.2 成功入队后一直没有速度

某次解析成功后，任务可以进入下载列表，但界面长期停留在类似状态：

```text
0 B / 483 B
--
```

其中 `483 B` 是 Telegram Document 元数据中的声明大小，不代表已经收到数据。`0 B` 表示扩展尚未观察到任何正进度，不能据此判断 Worker 内部具体卡在网络连接、首块请求、重试还是等待限流。

### 2.3 点击取消后一直显示“取消中”

用户点击取消后，日志确认扩展已经接受取消，并取得当前 `workerRequestId`：

```text
[DownloadManager] 已接受取消
[DownloadServices] 已接受活动下载取消
```

但任务没有从列表移除，长期显示“取消中”，后续等待任务也不会开始。

## 3. 排查结论

三个表象位于两个不同阶段，不能用一个根因解释：

| 阶段 | 已确认结论 | 确认程度 |
| --- | --- | --- |
| Document 参数解析 | 扩展的 LocalDb 镜像可能为空、不完整或监听了错误账号频道 | 根因已确认 |
| Worker 下载为 0 B | 扩展已创建 Worker waiter 和 requestId，但没有正进度和终态响应 | 所在阶段已确认，是否已进入 Worker 未确认 |
| 取消中不结束 | `cancelProgress` 只有单向通知，没有独立 ACK；扩展仍在等待原下载响应 | 原因已确认 |

### 3.1 Document 解析失败的根因

当前调用链如下：

```text
A 版 DOM 扫描
  -> 生成只有 chatId/messageId 的 Document placeholder
  -> 任务进入 FIFO 队首
  -> content 调用 getAMediaResources
  -> MAIN world 从 LocalDbMirror.documents 查询 Document
  -> 返回 documentId、mediaHash、文件名和大小
  -> 进入真实下载
```

这个 placeholder 合同本身没有问题。问题在 `extension/src/sites/telegram/injected/services/ALocalDbServices.ts` 的 LocalDb 镜像模型。

#### BroadcastChannel 不重放历史消息

LocalDb 镜像只被动监听 Telegram 的 BroadcastChannel。BroadcastChannel 只投递订阅之后的消息，不会向新订阅者重放此前的 `localDbUpdateFull`。

如果扩展初始化晚于 Telegram 的 full snapshot，镜像初始为空；只要 Telegram 后续既没有再次广播 full snapshot，也没有发送包含该 Document 的增量，对应查询就会持续失败。刷新后偶尔成功，是因为新的页面生命周期里碰巧收到了一次可补齐该 Document 的广播，不代表资源发生变化。

真实日志在成功前曾出现 `documents=766`、`documents=2955`、`documents=1241` 等全量更新，证明同一资源的随机成败由镜像同步时序决定。

#### 当前账号频道选择错误

当前实现依次尝试 `tt-global_1` 至 `tt-global_4`，并在第一次成功构造 BroadcastChannel 后停止。

构造 BroadcastChannel 成功只代表浏览器允许创建这个名称的频道，不能证明该频道存在 Telegram 发布者。因此循环总会停在 `tt-global_1`；当前页面如果是账号 2 或更高 slot，扩展会稳定监听错误频道。

Telegram 上游的频道名由 URL `account` 参数决定，规则位于 `src/util/multiaccount.ts` 的 `ACCOUNT_SLOT` 和 `DATA_BROADCAST_CHANNEL_NAME`。

#### 镜像范围与上游不一致

Telegram 上游 full snapshot 是账号级 LocalDb。扩展当前却执行以下聊天级行为：

- 增量更新按 `currentChatId` 过滤。
- 每 500ms 轮询聊天 URL。
- 聊天切换时清空整个镜像。

这使同一个镜像同时具有账号级 full snapshot 和聊天级 incremental/clear 两套语义。聊天切换后，扩展可能清空已经存在的 Document，并等待一个不一定再次出现的 full snapshot。

#### 上游已有主动全量刷新能力

Telegram Worker 的 `src/api/gramjs/localDb.ts` 已导出 `broadcastLocalDbUpdateFull`，并通过 `src/api/gramjs/methods/index.ts` 注册为可调用 Worker 方法。

扩展现有 A mediaHash 下载硬依赖当前 tab 已被 `WorkerInterceptor` 捕获的 GramJS Worker；Worker 为空时，`downloadMedia` 必然失败。本次故障日志已经取得 `workerRequestId`，而该 ID 只会在 Worker 已捕获后创建，因此本次 LocalDb miss 发生在已经持有当前 Worker 引用的页面。该 ID 在 `postMessage` 前创建，不能证明 Worker 已收到或开始执行请求。

未持有本地 Worker 的非 master tab 仍可能从账号频道被动收到 full snapshot。若只在 cache miss 时检查 Worker，cache hit 会先解析成功、随后扣除额度，再在真实下载阶段失败。因此 A Document 参数解析入口必须先检查当前 tab 是否已经捕获 Worker；未捕获时在额度检查前失败，不能把这条下游必败路径继续向前推进。

这里的检查只排除“当前没有已捕获 Worker”，不证明旧 Worker 仍然存活，也不保证检查后 Worker 不会终止。Worker 在检查后失效属于正常传输失败窗口，本轮不增加 ping、健康握手、跨 tab 下载或额度退款。

因此 cache miss 只复用现有 `WorkerInterceptor.callMethod` 调用当前 Worker 的 `broadcastLocalDbUpdateFull`。该调用会通过账号 BroadcastChannel 产生完整快照，不需要让用户刷新页面，也不增加跨 tab 协议、轮询、DOM 猜测或备用下载链。

### 3.2 0 B 任务当前处于什么状态

当前证据只能把任务定位到以下状态：

```text
DownloadManager 当前项 active
  -> DownloadServices 已调用 downloadMedia
  -> WorkerInterceptor 已创建 waiter 和 workerRequestId
  -> 是否已成功 postMessage 未记录
  -> 尚未收到正进度
  -> 尚未收到 methodResponse/error
```

现有日志没有记录“首次 callback”和“首次正进度”两个边界，因此还不能区分：

- Worker 请求只完成本地创建，尚未成功提交给浏览器 Worker 通道。
- `postMessage` 已返回，但 Worker 尚未开始回调；这仍不构成 Worker 已处理请求的 ACK。
- Worker 已回调 0，但首块文件请求未完成。
- Worker 正在断线重试。
- Worker 正在等待 FloodWait。
- Worker 内部存在其它未识别的 pending 阶段。

在没有新证据前，不得把网络、参数、Telegram API 或某个 GramJS 分支写成既定根因。

### 3.3 取消中不结束的原因

`extension/src/sites/telegram/injected/hooks/worker.ts` 向 Telegram Worker 发送：

```text
{ payloads: [{ type: "cancelProgress", messageId }] }
```

这个协议没有独立取消响应。上游只查找对应 progress callback，并设置 `isCanceled`。调用方只能确认取消 `postMessage` 未同步抛错，不能确认 Worker 已处理取消或真实下载已经停止。

上游下载过程只在部分阶段检查 `isCanceled`，各阶段边界如下：

- 单次 `sender.send` 与 60 秒 `SENDER_TIMEOUT` 竞争；取消标记通常要等本次发送返回后才会被检查。该上界只约束单次发送，不约束完整下载。
- `getSender` 会进入 exported sender 连接与重连流程；该流程存在持续重试，并且没有接入当前下载的取消标记，因此是首字节前长期 pending 的候选阶段，但尚未证明本次故障停在这里。
- `FloodWait` 直接按服务器返回的秒数 sleep，睡眠期间不检查取消，可使取消延迟数分钟。

这里不能把上游的 `sometimes a session is revoked and will cause this to hang` 注释当成 `getSender` 卡死的证据：该注释位于 `sender.send` 的 60 秒超时竞争前。`getSender` 的风险证据来自其下游 `_connectSender` 存在持续重试循环，二者是不同边界。

断线重试、sender 重建和 FloodWait 可以继续包围新的发送尝试，因此整个下载与取消流程仍没有已证明的有限上界。

扩展的 Worker waiter 当前使用 24 小时超时。发出取消后，`DownloadServices` 仍然等待原 `methodResponse`；因此从用户视角，任务可能长时间停留在“取消中”。

继续等待不是偶然实现细节，而是当前严格 FIFO 合同：旧 Worker 调用确认结束前，下载管理器不能启动下一项。Telegram Worker 会并发处理 `callMethod`；如果取消后立即在本地结算并推进队列，新旧真实下载可能重叠。

### 3.4 与 1.3.3 的关系

`v1.3.2..v1.3.3` 的源码差异显示：

- `ALocalDbServices` 和 `AMediaResourceService` 没有在 1.3.3 修改。
- A Document 点击时调用 `getAMediaResources` 的逻辑在 1.3.2 已存在。
- 1.3.3 增加了统一下载队列、任务状态和活动取消流程。

因此不能认定 LocalDb 解析根因由 1.3.3 引入。1.3.3 使“取消中”和严格 FIFO 阻塞变成了明确可见的用户状态，但 0 B 的底层 Worker 停滞原因仍需运行时证据。

## 4. 解决方案

### 4.1 将 LocalDb 统一为账号级镜像

`LocalDbMirror` 只维护当前 Telegram 账号的完整镜像：

1. 按 Telegram 上游的 URL `account` 规则计算 slot，只连接 `tt-global_{slot}`。
2. 删除频道 1 至 4 的试探连接。
3. 删除 `currentChatId`、500ms URL 轮询、聊天切换清空和 incremental peerId 过滤。
4. `localDbUpdateFull` 用新 snapshot 替换整个 photos/documents，不与旧镜像合并。
5. `localDbUpdate` 只对当前账号镜像做增量合并。
6. 查询仍按 `localRepairInfo.type=message + peerId + messageId` 精确过滤，不因镜像改为账号级而放宽资源归属。

该方案统一了 full、incremental 和查询的作用域，删除两套相互冲突的缓存语义。

### 4.2 cache miss 时主动刷新一次

`AMediaResourceService.getAMediaResources` 改为以下流程：

```text
检查当前 tab 已捕获 Worker
  -> 未捕获：立即失败，不进入额度检查
  -> 已捕获：按 identity 查询当前镜像
  -> 全部命中：直接返回
  -> 存在 miss：等待 single-flight refresh
  -> refresh 完成后重新查询一次
  -> 仍缺失：返回空结果，由现有调用方输出可定位错误
```

refresh 由 LocalDb 镜像 owner 管理：

1. 在调用 Worker 前注册当前账号频道的 `localDbUpdateFull` 等待条件，避免漏掉同步触发后的事件。
2. 复用 `WorkerInterceptor.callMethod('broadcastLocalDbUpdateFull', [])` 调用当前 tab 已捕获的 Worker。
3. 同时等到该 Worker 调用的 `methodResponse` 和 full snapshot，再按 identity 重查镜像。
4. 并发 cache miss 共享同一个 `refreshPromise`，不重复请求 full snapshot。
5. 成功、Worker 调用失败、响应缺失、full event 缺失或 deadline 到期都进入同一个清理出口，移除本次 listener、timer 和 `refreshPromise`。
6. 不增加自动重试、定时轮询或第二条 Document 下载路径。

上述调用失败、响应缺失、full event 缺失和 deadline 不是四套 fallback。LocalDb owner 只维护一个 in-flight Promise、一个 full snapshot listener、一个 timer 和一个幂等清理出口，各类终态收敛到同一出口。

refresh 复用现有 Worker waiter，不新增跨 tab 协议。未持有本地 Worker 的非 master tab 上，Telegram A 主消息 Document placeholder 解析与 mediaHash 下载不在本轮支持范围。

### 4.3 LocalDb 内层早于 EventRpc 外层超时

`EventRpcTransport.call` 当前按 `options.timeout -> transport timeout -> DEFAULT_RPC_TIMEOUT` 取值；`DEFAULT_RPC_TIMEOUT` 为 30 秒，`resolvePendingAMainDocument` 没有传 per-call options，因此外层当前就是 30 秒。

`WorkerInterceptor.callMethod` 增加可选 per-call timeout，默认仍使用下载调用所需的 24 小时；LocalDb refresh 显式传入 25 秒。full snapshot 等待使用同一 25 秒 deadline。25 秒是防止非下载调用无限等待的保护性预算，不是实测耗时结论；关键合同是 injected 内层必须早于 EventRpc 默认外层结束，为 provider 响应序列化和 DOM 事件派发保留时间。

content 继续使用现有默认 30 秒，不新增外层超时常量，不修改 `getAMediaResources` 调用参数，也不从 injected 实现模块导入配置。fake timer 测试必须直接锁定“25 秒内层先结算、30 秒外层仍未触发”。

LocalDb owner 在同一个终结路径清理 full snapshot listener、deadline timer 和 `refreshPromise`；`WorkerInterceptor` 按本次 per-call timeout 清理对应 waiter。fake timer 必须同时证明两处状态均不残留。

EventRpc 会掩码普通 handler Error，因此 content 不依赖详细阶段错误文本。具体失败阶段记录在 injected 的安全日志中；content 只依赖成功响应或标准 RPC 失败。

### 4.4 增加可确定任务状态的安全日志

Worker 下载链路增加以下阶段日志：

| 事件 | 能回答的问题 |
| --- | --- |
| `request created` | 是否已经创建 requestId 和本地 waiter |
| `postMessage succeeded` | 请求是否已经提交给浏览器 Worker 通道；不表示 Worker 已处理 |
| `first callback` | Worker 是否开始报告进度，包括 callback(0) |
| `first positive progress` | 是否已经收到首个有效文件分块 |
| `methodResponse` / `error` | Worker 是否已经结束调用 |
| `cancel posted` | 取消 `postMessage` 是否返回，以及对应哪个 requestId |
| `elapsed` | 每个阶段距请求开始经过多久 |

日志只记录 method、requestId、阶段、取消标记和耗时。禁止记录 `mediaHash`、文件 URL、`accessHash`、`fileReference` 或 Worker 返回的文件内容。

增加日志后，卡顿状态可按以下方式判断：

| 最后事件 | 状态判断 |
| --- | --- |
| `request created` | 本地请求已创建，尚未确认 `postMessage` 返回 |
| `postMessage succeeded` | 请求已提交给浏览器 Worker 通道，尚无 Worker 处理证据 |
| `first callback` 且无正进度 | 首字节前 pending |
| `first positive progress` 后停止 | 中途传输 pending |
| `cancel posted` 且无 methodResponse | 取消 `postMessage` 已返回，原 Worker 调用尚未结束 |
| 已有 methodResponse，但 UI 未结束 | 故障位于 Worker 之后的响应或队列收敛阶段 |

### 4.5 暂不提前结算 Worker 取消

本轮不在 `cancelProgress` 发出后立即 resolve，不隐藏仍活动的任务，也不推进下一 FIFO 项。

先通过新增阶段日志和真实环境实验确认：

- 取消是否最终总能返回 `methodResponse`。
- 首字节前 pending 和取消完成的实际耗时分布。
- 是否存在真实无限 pending。

如果证实 Worker 可以无限 pending，需要单独确认产品合同：

| 方向 | 行为 | 代价 |
| --- | --- | --- |
| 保持严格 FIFO | 旧 Worker 调用未结束时不启动下一项；用户刷新页面终止当前 Worker | 取消可能长期不结束 |
| 取消后立即推进 | 本地结算取消并启动下一项 | 新旧 Worker 请求可能短暂重叠，实际并发数不再保证为 1 |
| 宽限期后推进 | 取消后先等待根据真实耗时分布确定的宽限期，期满再本地结算并启动下一项 | 只是延迟接受重叠，不恢复严格 FIFO；旧 waiter 仍需独立清理 |

宽限期不能在没有真实耗时证据时预设为 90 秒；单次 `sender.send` 的 60 秒上界不能覆盖持续重连或 FloodWait。在确认修改 FIFO 合同前，不增加复杂超时状态机或猜测性 fallback。

## 6. 验证方案

### 6.1 Unit / Integration

- 当前账号为 2 时只连接 `tt-global_2`；默认账号连接 `tt-global_1`。
- full snapshot 替换旧 photos/documents，缺失集合按空集合处理。
- incremental update 在账号级镜像合并，聊天切换不清空。
- `gramJSWorker === null` 时，无论当前 identity cache hit 还是 miss，都在额度检查前失败。
- Worker 已捕获且 cache hit 时直接返回，不触发 full refresh。
- 首次 cache miss 触发一次 full refresh，refresh 后同一 identity 成功解析。
- 多个并发 miss 只调用一次 `broadcastLocalDbUpdateFull`。
- refresh 只调用当前 tab 已捕获 Worker 的 `callMethod`。
- Worker 调用失败、`methodResponse` 缺失和 full event 缺失都在 deadline 内失败。
- 所有成功和失败分支都清理 listener、timer、`refreshPromise` 和本次 Worker waiter。
- fake timer 证明 injected 25 秒先结算，content 默认 30 秒尚未触发。
- 模拟 callback(0) 后无正进度；取消后当前项保持 cancelling，下一项保持 waiting，原 methodResponse 后才推进 FIFO。

确定性 LocalDb 测试必须 mock 全局 BroadcastChannel、location 和当前 Worker，使用隔离频道，不接触 Telegram 自身 `tt-global_*`。

### 6.2 真实浏览器

真实验收使用 production build 和固定 Telegram profile：

1. 确认当前页面已经捕获 GramJS Worker。
2. 在自然出现的镜像 miss 日志后，首次点击固定 Document。
3. 断言同一次点击通过当前 Worker 调用一次 `broadcastLocalDbUpdateFull`。
4. 断言收到非空 full snapshot，并按原 `chatId + messageId` 命中 Document。
5. 断言不刷新页面即可进入 `downloadMedia`。
6. 观察 Worker 阶段日志，记录 0 B 任务最后停留阶段和取消完成时间。

禁止向真实 `tt-global_{slot}` 广播空 `localDbUpdateFull`。Telegram 非 master tab 会用该消息覆盖主线程 `savedLocalDb`；该缓存是该 tab 未来升为 master 时初始化 Worker 的种子，空快照会污染被测系统并让后续结果失真。真实 cache miss 只使用自然场景人工验证，不通过空快照注入制造，也不作为 CI 门禁。

## 7. 验收标准

- LocalDb 尚未同步时，用户第一次点击 Document 会主动 refresh，并在同一次操作中继续解析，不再依赖刷新网页。
- 多账号页面使用与 Telegram 当前账号一致的 BroadcastChannel。
- 聊天切换不会破坏账号级 LocalDb 镜像。
- Telegram A 主消息 Document placeholder 查询时，当前 tab 未捕获 Worker 则 cache hit 和 miss 都在额度检查前失败。
- 当前 tab 已捕获 Worker 时，cache miss 通过现有 `callMethod` 请求 full snapshot。
- full refresh 失败有 25 秒有限上界，且不残留 listener、timer、single-flight Promise 或本次 Worker waiter。
- EventRpc 默认 30 秒外层不会与 25 秒内层同时超时并覆盖真实执行结果。
- refresh 后仍不存在对应 Document 时，当前项明确失败，FIFO 继续后续任务。
- 日志可以区分 Worker 未 callback、首字节前 pending、中途 pending、取消等待和 Worker 后处理五类阶段。
- 取消期间下一项不启动；原 Worker 终态到达后当前项移除并继续 FIFO。
- 日志不包含 Telegram 下载引用、访问凭证、文件地址或文件内容。
- A/K 现有 photo、video、album、Sidebar、Story 和普通 Document 下载测试无回归。

本计划完成 LocalDb 修复并不等于已经修复所有 Worker 0 B 问题。只有运行时证据确认具体 pending 阶段并完成对应修复后，才能关闭 0 B 故障；如果需要修改严格 FIFO 合同，必须单独确认后再实施。

本轮不支持未捕获本地 Worker 的非 master tab 执行 Telegram A 主消息 Document mediaHash 下载。Worker 前置检查也不保证旧 Worker 持续存活；检查后 Worker 终止仍按现有单项下载失败处理，不增加健康握手或退款。
