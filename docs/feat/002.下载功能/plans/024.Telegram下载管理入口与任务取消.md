# 024 · Telegram 下载管理入口与任务取消

> 状态：实现与确定性验证已完成；真实 Telegram A/K 验收因登录态过期阻塞，本计划尚未完成。

## 1. 目标

- 在 Telegram A/K 主聊天列右下区域注入当前 document 的下载管理入口，展示未完成数量、最终保存文件名、状态、进度、文件大小和下载速度。
- 页面入口与 Extension Popup 展示同一份 FIFO 快照；共享 Popup 可移除各平台等待任务，Telegram 页面与 Popup 可按唯一任务中止快照声明可取消的活动传输。
- 等待任务取消后不进入额度检查；活动任务确认传输停止后再移除，并继续执行下一项。
- Blob、HTTPS 分块和 Telegram A `mediaHash` 三条真实下载路径都支持停止传输，不把 UI 移除当成取消完成。
- 真实失败保留在唯一任务列表，后续等待项继续；页面与 Popup 可人工重试，Telegram 页面可批量清空等待或清除全部。

## 2. 非目标

- 不为 X、Instagram、Threads、Vimeo 或其它平台增加页面取消入口或活动传输中止；Popup 移除各平台 waiting 是共享 FIFO 能力，不属于 Telegram active abort 范围。
- 不做跨标签页聚合、页面刷新后的任务恢复、下载历史、暂停、手工重排或自动重试；清除全部只作用于当前页面运行时任务。
- 不新增持久化状态、后台恢复、第二套队列、第二条 EventRpc transport、Port、第三方依赖或依赖注入。
- 不修改额度规则；已经成功消耗的额度不退款。
- 不保证真实下载速度的固定数值；只保证字节来源、计算口径和精确/估算标识正确。

## 3. 依赖与证据

- 产品行为与 UI 以 `@../feat.md` 的“Extension Popup 下载状态”和“Telegram 页面下载入口”为唯一规格。
- 技术合同以 `@../tech-扩展端TG扫描.md` 的 Plan 024 目标合同为基线。
- 当前唯一 FIFO 与 Popup 唯一事实源是 `extension/src/core/content/download/downloadManager.ts`；页面入口必须订阅这份快照，不复制任务数组或排序规则。
- 当前任务 ID 由 document `scopeId` 与自增序号组成，同一资源重复入队仍有不同任务 ID；取消只按任务 ID。
- 当前 EventRpc 每次调用使用独立 request ID，provider 对事件独立执行。长 `downloadMedia` 未结束时可在同一 channel 并发处理取消，无需新增 transport 或 client。
- Blob 与 HTTPS 分块下载都基于 `fetch`，可通过同一任务的 `AbortSignal` 停止请求；已聚合字节必须在取消终态释放。
- Telegram A Worker 上游 `Ajaxy/telegram-tt@8b63941b230b3870accc442b5ef5ac95fc53c719` 定义了 `{type:'cancelProgress', messageId}`，外层消息为 `{payloads:[...]}`；类型见 [`types.ts#L80-L86`](https://github.com/Ajaxy/telegram-tt/blob/8b63941b230b3870accc442b5ef5ac95fc53c719/src/api/gramjs/worker/types.ts#L80-L86)，接收与执行见 [`worker.ts#L52-L54`](https://github.com/Ajaxy/telegram-tt/blob/8b63941b230b3870accc442b5ef5ac95fc53c719/src/api/gramjs/worker/worker.ts#L52-L54) 和 [`worker.ts#L124-L130`](https://github.com/Ajaxy/telegram-tt/blob/8b63941b230b3870accc442b5ef5ac95fc53c719/src/api/gramjs/worker/worker.ts#L124-L130)。用户真实页面日志已证明取消响应以 `USER_CANCELED` message 到达当前 Worker interceptor。
- 上游 `cancelProgress` 没有独立响应。取消方法只能确认任务存在且中止操作已经发出，真正终态必须等待原长下载调用结束；发布前必须用真实 Telegram A 页面证明当前部署 Worker 确实停止 `mediaHash` 请求。
- EventRpc 响应只序列化成功状态、错误码和错误文本，不保留自定义 Error 类型；取消终态使用明确响应字段，不依赖跨 realm 的 Error class。

## 4. 已确认决策

1. 只覆盖 Telegram 当前 document；页面刷新或关闭后不恢复任务。
2. 页面入口由 Telegram content 初始化创建；A `8b63941` 插入 `.middle-column-footer` 原生 arrow-down wrapper 前，K `b21491` 挂在活动输入容器并按可见 mention/reaction/poll 数量占用 jump-down 上方下一格。空队列继续隐藏。
3. 页面入口与 Popup 只渲染同一个 `DownloadQueueSnapshot`。页面在 content 内直接订阅，Popup 继续通过 Chrome EventBus 与 `getDownloadQueue` 读取。
4. 页面入口直接调用同一个下载管理器取消、重试和批量清理；Popup 通过 content RPC 调用取消与重试。
5. 取消与重试键是 `taskId`，不是 `resourceId`。重复入队的同一资源必须保持独立任务身份。
6. Blob 与分块路径按真实响应字节计算速度；A `mediaHash` 只有百分比时按已知总大小估算，并显示 `≈`。
7. 文件名始终以实际保存名为准。A 主消息 Document placeholder 在等待队首解析时显示“获取文件名中…”；解析完成后先更新原名或保存兜底名，再开始额度检查。Blob 响应 MIME 修正扩展名时，在保存前再次更新快照，不能让列表名称与最终落盘名称分叉。
8. 等待任务取消立即完成调用方 Promise，不记录失败；活动任务先显示取消中，收到真实传输取消终态后才完成 Promise、移除任务并推进 FIFO。
9. 失败项不阻断后续 waiting；管理器用显式活动任务 ID 驱动进度和取消，不能假设数组首项是活动项。
10. 页面入口总数包含 failed；顶部清除全部一次处理 waiting+failed+downloading，等待分组清空只处理 waiting，均不弹确认框。

## 5. 复杂度闸门

本计划新增两项运行时机制，触发 `hydra-feat` 复杂度闸门：

| 机制 | 必要证据 | 最小代价 | 简单替代方案及缺口 |
|---|---|---|---|
| 既有任务增加 `cancelling` 状态 | 活动下载是跨 content/injected 的长异步调用；立即移除会让 FIFO 启动下一项并与尚未停止的传输并发 | 只扩展既有内存任务状态，不持久化，不增加独立状态机对象 | 只允许取消等待任务；无法满足“开始下载后可以取消” |
| injected 单一活动传输控制项 | 取消 RPC 只有任务 ID；Blob、分块 fetch 和 Worker request 必须找到当前 AbortController 或 Worker message ID | 复用 FIFO 同时只有一个活动任务的事实，只保存一个短命控制项，完成、失败或取消后清空 | 刷新页面终止全部传输；无法取消指定任务，也无法保留队列后续项 |

用户已追加批准失败保留、人工重试和批量清理；仍不包含持久化、补偿、自动重试或多任务并发控制。

## 6. 状态与接口合同

### 6.1 下载任务快照

`DownloadTaskSnapshot` 在既有对象上扩展，不新增页面专用任务模型：

| 字段 | 目标合同 |
|---|---|
| `taskId` | 当前 document 内唯一；所有取消入口只提交该值 |
| `filename` | 可选；缺失时 UI 显示“获取文件名中…”，队首解析或 Blob 响应格式确认后必须在保存前更新为最终保存名 |
| `status` | `waiting / downloading / cancelling / failed`；取消完成后移除，真实失败保留到人工重试或清除全部 |
| `activeTransferCancellable` | enqueue 时按真实 `sourceKind` 能力确定；只控制活动传输中止，waiting 本地移除不受影响 |
| `progress` | 0-100；不能计算时为 `null` |
| `receivedBytes` | 真实或估算已接收字节；没有可靠来源时为 `null` |
| `totalBytes` | 优先使用传输响应总大小，其次使用资源声明大小；未知为 `null` |
| `bytesPerSecond` | 最近 3 秒累计字节样本的窗口平均；有效跨度至少 500ms，等待、取消中或未知时为 `null` |
| `bytesAreEstimated` | 只有 A `mediaHash` 百分比换算字节时为 `true` |

### 6.2 状态转换

| 当前状态 | 事件 | 结果 |
|---|---|---|
| `waiting` | 用户取消 | 从 FIFO 删除，完成调用方 Promise，不调用额度，不影响其它任务顺序 |
| `waiting` | 成为队首 | 进入 `downloading`，解析实际资源并执行额度检查 |
| `downloading` | 用户取消 | 进入 `cancelling`；停止更新速度并请求取消当前阶段或真实传输 |
| `cancelling` | 解析或额度请求返回 | 不再启动 injected 传输；按取消终态完成 |
| `cancelling` | 传输确认停止 | 移除任务、完成调用方 Promise、继续下一项 |
| `downloading` | 正常失败 | 保持失败日志与首次调用方 reject，转为 `failed` 并继续查找后续 `waiting` |
| `failed` | 人工重试 | 恢复初始资源与展示字段，移到 FIFO 尾部为 `waiting`，本次及后续人工重试跳过额度检查 |
| `waiting` | 清空等待 | 与全部 waiting 一次移除并完成原调用方 Promise，只发布一次快照 |
| `waiting / failed / downloading` | 清除全部 | waiting+failed 一次移除；downloading 转 cancelling 并等待真实取消终态；既有 cancelling 保留 |

### 6.3 RPC 合同

- content `cancelDownloadTask({taskId}) -> {accepted:boolean}`：Popup 取消当前目标 tab 的唯一任务。任务已经结束或不属于该 document 时返回 `false` 并刷新快照。
- content `retryDownloadTask({taskId}) -> {accepted:boolean}`：Popup 重试当前目标 tab 的失败任务；其它状态、已结束或其它 document 返回 `false` 并刷新快照。
- injected `downloadMedia({taskId, source}) -> {success:true, cancelled:boolean}`：正常完成返回 `cancelled:false`，取消完成返回 `cancelled:true`。
- injected `cancelDownloadMedia({taskId}) -> {accepted:boolean}`：找到活动任务并成功发出中止操作返回 `true`；任务不存在、已经完成或中止操作未发出返回 `false`。该响应不是取消终态。
- `downloadProgress` 增加任务 ID、资源 ID、进度、已接收字节、总字节、估算标记和可选的已确认保存文件名。content 只接受同时匹配显式活动任务 ID 与资源 ID 的展示数据；该 DOM 事件不能改变额度、完成或取消终态。

## 8. 分阶段实施

### 8.1 快照、取消语义与共享格式化

- 扩展既有任务快照与下载管理器；等待取消、活动取消、A placeholder 解析后文件名更新、Blob 响应扩展名回写和速度采样都在唯一 FIFO 内完成。
- content register 和通用 MessageHandler 增加取消 RPC 并重新生成 typed client；Popup 对各平台 waiting 显示本地移除，对 `activeTransferCancellable` 为 true 的活动任务显示真实中止，不按目标 URL 判断能力。
- 抽取文件大小、速度和估算标识的共享纯格式化函数，页面和 Popup 使用同一口径。
- 先完成下载管理器、快照版本和 Popup store 的 Unit 测试。

验收：重复资源逐任务取消；等待取消不调用额度；活动取消期间下一项不启动；取消完成后 FIFO 继续；文件名与实际传给保存层的名称一致。

### 8.2 injected 真实传输取消与指标

- `downloadMedia` 增加任务 ID；Telegram injected 复用 FIFO 单活动任务约束，只维护一个短命活动传输控制项。
- Blob 与 Segment 下载器接收同一任务的 `AbortSignal`，每次真实读取上报字节；取消时中止 fetch、重试等待和聚合，并释放引用。
- A Worker 下载开始后把当前 request ID 放入同一个活动控制项；取消时发送 `{payloads:[{type:'cancelProgress',messageId:requestId}]}`，完成后随控制项一起清理。
- 长下载与取消 RPC 均返回明确取消结果，不依赖自定义 Error 穿过 EventRpc。

验收：三条传输路径都只有真实停止后才返回取消；取消不会触发浏览器保存、失败埋点或失败提示；控制项在完成、失败、取消后均不存在。

### 8.3 Telegram 页面入口与 Popup

- Telegram content 初始化创建 document 级页面 owner，并在销毁时移除根节点、订阅与 observer；新 CSS 按现有 Telegram 样式机制登记到平台资源注册表并由 content 加载。
- A/K 分别使用已确认源码版本的原生向下浮动控件锚点；K 只计算统一未读控件的可见数量，不扫描通用 button 或使用聊天列固定坐标。
- 按 `feat.md` 实现页面入口、数量徽章、浮层、键盘/触屏交互、亮暗主题与 reduced-motion。
- Popup 按快照字段展示大小、速度和取消中状态；各平台 waiting 都显示本地移除，活动取消按钮只由 `activeTransferCancellable` 决定，当前只有 Telegram 活动传输具备该能力。
- 所有新增可见文案与可访问名称进入现有 i18n 清单；不硬编码中文或英文。

验收：A/K 页面入口与 Popup 同步显示同一任务；两处取消任一项后同时更新；320px Popup 与窄 viewport 页面均不越界、无横向滚动。

### 8.4 真实 Telegram 验收与文档收口

- fresh production build 后使用固定 Telegram profile，在真实 A/K 页面执行页面入口、Popup 同步、等待取消、活动取消和后续任务继续。
- 真实页面、媒体请求、扩展 RPC、Worker 与 Chrome 下载均不 mock；只允许按现有规范固定 quota check 与 SLS sink。
- 验证当前部署 Telegram A Worker 接受 `cancelProgress`。若真实 A 传输没有停止，本计划不能记为完成，也不能把任务从 UI 移除；记录真实 payload/响应证据后回到设计确认，不添加猜测性兼容分支。
- 同步 `feat.md`、技术文档、E2E 文档与 changelog，移除已完成计划中的“待批准”标记并记录实际验证结果。

## 9. 验证计划

### Unit / Integration

- 在既有下载队列测试中覆盖两个直接行为：等待任务取消不调用额度；活动任务取消期间不启动下一项，终态后继续 FIFO。
- 在既有下载器与 Worker 生命周期测试中覆盖 `AbortSignal` 中止，以及 `cancelProgress` 使用当前 request ID 和 `payloads` 外层；不为 Blob、Segment 和 Worker 复制同构测试。
- 在既有 Popup/UI 测试中覆盖文件名、大小、速度、取消中状态与取消按钮；页面入口的悬浮、点击和键盘行为合并到一个组件测试。
- A placeholder 文件名更新与 Blob 实际扩展名回写合并到对应现有下载链测试，不新建只验证字段存在的测试。

### E2E

- A/K 页面入口与 Popup 对同一 FIFO 的数量、文件名、状态、进度和大小一致。
- 等待任务从任一入口取消后立即消失，quota check 次数不增加。
- 活动任务取消后真实媒体读取停止、不产生该任务落盘文件，下一项继续并成功落盘。
- A `mediaHash` 用真实 Worker 验证 `cancelProgress`；K 使用一条稳定真实下载路径验证活动取消。Blob/Segment 的确定性 abort 行为合并到现有下载器测试，不为每条同构路径增加 E2E。
- E2E 不伪造下载节奏，不断言固定速度值；500ms 固定采样、EMA 平滑、3 秒停滞清空、AbortController 和 Worker payload 由 Unit/Integration 提供确定性证据。

1. 用户明确批准 §5 两项复杂度机制后才开始实现。
2. `pnpm rpc-generate:check`、`pnpm check`、`pnpm test:unit:run` 和目标 Telegram 真实 E2E 通过。

5. 当前部署 Telegram A Worker 的取消合同有真实 E2E 证据；没有证据不能标记完成。
6. 本计划以外的平台不增加页面取消入口或活动传输中止；共享 Popup 仍为其 waiting 任务提供本地移除。
