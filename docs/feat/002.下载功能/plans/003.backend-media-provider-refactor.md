# 003 · 后端媒体 Provider 架构重构执行计划

## 1. 目标

把后端 V2 parse/download 执行层从 `MediaNodeExecutionService` 拆成统一 `media_provider_service` + 每平台一个 Provider，支持后续几十个平台接入，并补上 proxy 用户活跃下载并发限制。

本轮最终口径：

- 用户活跃下载上限为 2。
- 并发限制由 `provider.policy.active_limited` 决定，不由 `download_mode` 推导。
- 计数只使用进程内 dict，不使用 Redis。
- 当前 direct / client_mux Provider 默认不进入活跃下载计数。
- Provider 声明 `ProviderPolicy(active_limited, bandwidth_limited)`。
- Range 由 Provider 按本次资源和上游响应决定，公共层只透传 `Range` 头。
- Provider parse 可在每个 resource 上写内部 `extra`，公共层只签名透传给同平台 Provider download。
- 每次 stream result 自带本次资源的 `aclose`，不做 `provider.release()`。
- proxy 文件响应关键头由 API/service 从 `StreamDownloadResult` 结构化字段生成，Provider 只返回 `filename`、size/range 字段和可选 `extra_headers`。

## 4. 阶段拆分

### Phase 1 · 契约层与 service 骨架

目标：

- 新增 `provider/media/base_media.py`。
- 定义 `ProviderPolicy`、`MediaParseRequest`、`MediaDownloadRequest`、`MediaParseResult`、`StreamDownloadResult`、`JsonDownloadResult`、`MediaProviderError`。
- 定义显式 provider registry：`MEDIA_PROVIDERS: dict[str, BaseMedia]` 与 `get_media_provider(platform)`。
- 新增 `services/media_provider_service.py`，先提供 `get_provider()`、`parse_v2()`、`download_v2()` 的目标入口。
- `MediaParseResult.response.resources[*].extra` 是后端内部字段;公开 JSON 序列化必须排除 `extra`。
- resource token 与 media download token 只原样签名透传 `extra`,公共层不读取其内部字段。
- `media_resource_token_service.py`、`media_download_token_service.py` 和相关 claims/schema 必须使用统一 `extra` object；`uid` 与 `extra` 按新 token 契约签发。
- `extra` 必须校验为短小 JSON object：compact JSON 不超过 2048 bytes、最大深度不超过 4；下载必需的缓存 key 必须可跨候选下载节点解释。当前重构不允许把必需的节点本地缓存 key 写入 token。
- 平台逻辑按阶段搬入 Provider；`media_provider_service` 不新增转调 `media_node_execution_service` 的过渡路径。

验收：

- 类型定义清晰，后续平台文件无需再新增请求/结果基类。
- registry 是显式 dict,不做自动扫描、不做装饰器注册。
- `extra` 不出现在 parse-v2 公开 JSON。
- parse-v2 公开 resource 必须包含 `resource_token`,不能包含 `resources[].extra`。
- URL 平台识别失败与 registry 缺 Provider 能区分：前者是 unsupported platform，后者是 node unavailable + `reason=provider_missing`。
- API 尚未切流时，现有行为不变。

### Phase 2 · 活跃下载计数

目标：

- 新增 `media_active_download_service.py`。
- `acquire(user_key)` 成功返回幂等 guard;上限 2 在 service 内部固定。
- 超过上限返回 `RATE_LIMIT_EXCEEDED_MEDIA`, `data.reason = "active_download_limit_exceeded"`。
- 只在 `provider.policy.active_limited=True` 时进入计数。
- provider 打开资源失败、stream 正常结束、stream 报错、客户端断开、BackgroundTask 兜底都必须释放。
- Provider 返回 result 前抛错时，公共层用预置 no-op `provider_aclose` 释放 active guard；Provider 自身负责关闭已部分打开的平台资源。

验收：

- 同一用户第 1、2 个 active-limited 下载允许。
- 同一用户第 3 个 active-limited 下载返回 `RATE_LIMIT_EXCEEDED_MEDIA`,且前端不切节点。
- `active_limited=False` 的 Provider 不占计数。
- `release()` 重复调用不会减成负数。
- provider `aclose()` 抛错时,active guard 仍会在 `finally` 中释放。
- provider 返回结果类型与 `claims.download_mode` 不匹配时,先释放 guard,再返回节点不可用错误。
- BackgroundTask 必须挂 `release_once`,不能直接挂 provider `aclose`。
- 进程重启后计数自然清空。

### Phase 3 · Telegram / TikTok proxy Provider

目标：

- 新增 `telegram_media.py` 和 `tiktok_media.py`。
- 搬出 TG proxy 和 TikTok proxy 的打开资源、stream、provider `aclose`。
- Range/header 构造使用同一套 Provider 内 helper;公共层只透传原始 `Range` 头。
- Telegram / TikTok Provider 按本次资源和上游响应决定 Range 成功或 `RANGE_NOT_SATISFIABLE`。
- 输出 chunk 由 `media_provider_service` 统一接入 `proxy_bandwidth_limit_service`。

验收：

- TG proxy 下载、Range 下载、0 字节、未知大小 4GiB 保护行为不变。
- TikTok proxy 下载、上游 206/416/403/5xx 行为不变。
- TG/TikTok 的资源释放收敛到 Provider result 的 `aclose`。

### Phase 4 · direct / client_mux 平台 Provider

目标：

- 每个平台一个 Provider 文件：
  - `vimeo_media.py`
  - `x_media.py`
  - `instagram_media.py`
  - `threads_media.py`
  - `reddit_media.py`
  - `douyin_media.py`
- direct 返回 `JsonDownloadResult(MediaDirectDownloadIntentResponse)`。
- reddit 视频返回 `JsonDownloadResult(MediaClientMuxDownloadIntentResponse)`。
- 不新增 `direct_media.py`。

验收：

- direct/client_mux 的 JSON schema 与 V2 API 契约一致。
- 新增平台复用已有 `download_mode` 时不需要改 `media_provider_service` 主流程。

### Phase 5 · 删除旧执行 service

目标：

- `api/client/media_v2_client.py` 改调 `media_provider_service`。
- 删除 `MediaNodeExecutionService` 兼容壳；平台执行代码迁入对应 Provider。
- 删除 `media_parse_service.py` 旧平台分发入口；后台诊断也通过 Provider registry 解析。
- 清理重复 Range/header/error helper。
- 同步文档中的文件名和流程口径。

验收：

- 代码中不存在 `MediaNodeExecutionService` / `media_parse_service` 引用。
- 新平台接入只动 provider 文件、registry、测试、站点文档。
  新增 mode 时另行补 schema、前端 runner、方法注册和接口文档。

## 5. 测试策略

单元测试：

- `media_active_download_service.acquire/release`：
  - 上限 2。
  - 第 3 个失败。
  - 幂等 release。
  - 不同用户互不影响。
- `media_provider_service.parse_v2`：
  - resource 内部 `extra` 写入该 resource token。
  - parse-v2 公开 JSON 不包含 extra。
  - parse-v2 公开 JSON 包含 `resource_token`,且不包含 `resources[].extra`。
  - Telegram `tg_client_ref` 进入 `extra`,不再作为公共 claims 一等字段。
  - `extra` 超过 2048 bytes、非 JSON object 或嵌套过深时不签发 token,返回 `MEDIA_PARSE_NODE_UNAVAILABLE` + `data.reason=invalid_extra`。
  - `extra` 中下载必需的缓存 key 必须指向共享缓存；节点本地材料只能作为可失效 hint。
  - URL 平台识别失败返回 `MEDIA_PARSE_UNSUPPORTED_PLATFORM`。
  - registry 缺 Provider 返回 `MEDIA_PARSE_NODE_UNAVAILABLE` 且 `data.reason=provider_missing`。
  - `parse_v2` 构造 `MediaParseRequest(url, user_id, device_id, client_ip)` 传给 Provider;匿名或非法身份按 user -> device -> IP 限流回退。
- `media_provider_service.download_v2`：
  - `provider.policy.active_limited=True` 才 acquire。
  - `provider.policy.active_limited=False` 不 acquire。
  - 请求带 Range 时仍调用 Provider,由 Provider 决定返回 206 或 `RANGE_NOT_SATISFIABLE`。
  - token 已知 `size > 4GiB` 时不 acquire、不调用 provider。
  - provider `StreamDownloadResult.total_size > 4GiB` 时 release 并返回文件过大。
  - provider.download 返回 result 前抛错后 release active guard。
  - provider.download 成功后公共校验失败会 release。
  - provider.aclose 抛错后 active guard 仍 release。
  - `release_once` 调用包装前保存的 provider `aclose`,不会递归调用包装后的 `aclose`。
  - mode 与 result 类型不匹配时 release 并返回节点不可用。
  - direct/client_mux 的 JSON payload schema 不匹配时返回节点不可用。
  - stream finally 与 aclose 双调用只 release 一次。
  - `MediaProviderErrorCode` 正确映射到 `CommonCode`。
  - `bandwidth_limited=False` 只跳过输出限速；是否 acquire 只看 `active_limited`。
  - registry 缺 Provider 返回 `MEDIA_DOWNLOAD_NODE_UNAVAILABLE` 且 `data.reason=provider_missing`。
  - extra 中下载必需的缓存 key 必须指向共享缓存；节点本地材料缺失时必须能降级,不能让已扣费下载依赖节点本地缓存。

API 层回归测试：

- `download-v2` token 无效/过期仍返回 HTTP 401。
- `MEDIA_RANGE_NOT_SATISFIABLE` 仍返回 HTTP 416,并从 `MediaProviderError.data.content_range` 透传 `Content-Range`。
- `MEDIA_DOWNLOAD_NODE_UNAVAILABLE`、`MEDIA_DOWNLOAD_RESOURCE_UNREACHABLE`、`MEDIA_DOWNLOAD_FILE_TOO_LARGE`、`RATE_LIMIT_EXCEEDED_MEDIA` 仍按现行契约返回 HTTP 200 envelope。
- 所有 `download-v2` 成功/错误响应保留 `Cache-Control: no-store`。
- proxy `StreamingResponse` 创建失败时仍调用 `release_once()`。
- proxy 文件流成功响应必须由 API/service 根据 `StreamDownloadResult.filename` 清理、编码并生成 `Content-Disposition: attachment; filename="<safe-ascii-fallback>"; filename*=UTF-8''...`;HTTP 200 JSON envelope 禁止带该头。
- `StreamDownloadResult.filename` 包含 CR/LF、路径分隔符、危险引号或非 ASCII 字符时,响应头仍合法且不可注入;非 ASCII 通过 RFC 5987 `filename*` 编码。
- ASCII fallback 必须尽量保留安全文件 stem/扩展名,为空时才用 `download`。
- `Content-Length`、`Content-Range`、`Accept-Ranges` 由结构化字段生成,不是 Provider 手写关键头。
- `extra_headers` 只允许 `ETag`、`Last-Modified`;禁止 `Set-Cookie`、`Location`、`Content-*`、`Transfer-Encoding` 等关键或危险头。
- proxy 下载器无 attachment 头时按 JSON envelope 处理;合法 `application/json` 文件带 attachment 头时仍按文件处理。
- `MEDIA_DOWNLOAD_RESOURCE_UNREACHABLE` 不触发前端切节点;只有网络/网关错误和 `MEDIA_DOWNLOAD_NODE_UNAVAILABLE` 切节点。

前端验收：

- HTTP 200 且无 `Content-Disposition: attachment` 时按 JSON envelope 读取业务 code。
- 带 `Content-Disposition: attachment` 的 `application/json` 响应仍按文件保存。
- direct URL 过期或 CDN 失败时,`direct-download.ts` 最多重新走一次 `download-pre-v2 -> download-v2` 获取 direct JSON。
- client_mux track fetch 失败时,`client-mux-download.ts` 最多重新走一次 `download-pre-v2 -> download-v2` 获取 tracks JSON。
- `MEDIA_DOWNLOAD_RESOURCE_UNREACHABLE` 不切下载节点。
- `RATE_LIMIT_EXCEEDED_MEDIA` 不切下载节点。
- `MEDIA_DOWNLOAD_NODE_UNAVAILABLE` 才按候选下载节点顺序切换。

集成/回归：

- TG proxy 普通下载。
- TG proxy Range 续传。
- TikTok proxy 普通下载。
- direct 平台返回 JSON result。
- reddit client_mux 返回 tracks JSON。
- `download-v2` 错误响应仍带 `Cache-Control: no-store`。
- 前端 proxy response 判别不依赖 `Content-Type`。

## 6. 风险与回滚

风险：

- stream 生命周期包装错误会导致用户计数泄漏。
- provider `aclose` 和 service `release_once` 双重调用会导致重复释放。
- Range/header 搬迁时可能改变续传行为。

控制：

- `release_once` 必须幂等。
- active guard release 必须幂等。
- Phase 2 先补并发释放测试，再搬平台。
- TG/TikTok proxy 先迁移，因为它们最依赖释放正确性。
- `extra` 只允许短小 JSON 定位材料;敏感内容使用加密 token 或缓存 key。
- `extra` 中下载必需的缓存 key 默认使用共享缓存;如果平台必须用节点本地缓存,节点候选过滤、扣费顺序和错误语义必须在该平台接入文档中单独写清。

回滚：

- 发布失败时回滚后端版本。
- 并发限制出现误杀时回滚 Phase 2 代码或上一版后端；本方案不新增运行时开关。
