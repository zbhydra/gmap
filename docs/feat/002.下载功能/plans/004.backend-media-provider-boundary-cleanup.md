# 004 · 后端媒体 Provider 边界收口执行计划

## 1. 目标

把所有媒体平台实现真正收口到 `backend/src/app/provider/media/`：

- `provider/media` 内部禁止调用 `app.services`。
- 每个平台一个 Provider 类，Provider 只承担本平台 `parse` / `download` / 平台私有 helper。
- 删除旧平台 `*_client_service.py`，不保留薄壳或反向转调。
- Telegram 也纳入同一规则；TG 媒体解析、下载、请求级上下文、换号重试和 release 在 `TelegramMedia`，TG 账号池生命周期在 `telegram_manager.py`。
- 后续新增平台时，只新增平台 Provider、registry、平台测试和站点文档，不把平台逻辑塞回 service。

## 2. 非目标

- 不改 V2 外部 API 路径、请求体和响应体。
- 不改 `proxy` / `direct` / `client_mux` 三种下载模式语义。
- 不引入依赖注入。
- 不新增共享 `direct_media.py`、`proxy_media.py` 或平台分发 service。
- 不把 FastAPI `StreamingResponse` 下沉进 Provider。
- 不把并发计数、带宽 bucket、BackgroundTask 实现传进 Provider。
- 不把全局账号池、HTTP client、browser runtime 这类基础设施塞进 Provider 单例；这些生命周期放在 `app/provider/` 下的非 service 基础设施模块。
- 不改 `media_service.py` 承担的 pre-v2 扣费、去重和 admin download analytics 口径。

## 3. 原始问题与当前状态

本计划处理的原始边界裂缝：

- `instagram_media.py`、`threads_media.py`、`x_media.py`、`vimeo_media.py`、`reddit_media.py`、`douyin_media.py`、`tiktok_media.py` 仍调用旧平台 `*_client_service.py`。
- `telegram_media.py` 仍调用 `tg_client_service`。
- `media_platform_service.py` 这类媒体契约放在 `services` 下，导致 Provider 依赖 service 命名空间。
- 旧平台 service 仍保留大量平台逻辑，Provider 只是薄壳。
- 旧平台 service 还依赖 `browser_runtime`、`meta_media_url`、`meta_ssr_extractor`、`x_cookie_file_service` 等 service 命名空间模块；这些依赖若不一起迁出，Provider 仍会违反边界。

当前代码边界：

- `provider/media` 对 `app.services` 零依赖。
- Telegram 媒体 parse/download/request context/release 已收口到 `TelegramMedia`。
- Telegram 账号池生命周期只在 `telegram_manager.py`。
- 旧平台 service 与旧 TG runtime 门面不作为当前设计保留。

## 4. 硬性边界

### 4.1 Provider 层禁止依赖 service

仓库根执行：

```bash
rg "app\\.services" \
  backend/src/app/provider/media \
  backend/src/app/provider/telegram_manager.py \
  backend/src/app/provider/browser_runtime.py \
  backend/src/app/provider/x_cookie_pool.py \
  backend/src/app/contracts/media_platform.py \
  backend/src/app/contracts/media_download.py \
  backend/src/app/constants/media_download.py
```

结果必须为空。任何例外都必须先取得 Hydra 明确同意。

### 4.2 Provider 文件结构

每个平台文件允许保留：

- 文件顶部用途注释。
- 平台常量。
- dataclass / Protocol / 类型别名。
- Provider class。
- 模块级 Provider 单例。

平台私有 helper 必须成为 Provider class 方法，通过 `self.xxx()` 调用。

### 4.3 provider 基础设施与 service 边界

有状态基础设施不属于业务 service：

- TG 账号池、session、lease、client 删除、心跳、startup/shutdown 和 session count：继续由既有 `app/provider/telegram_manager.py` 承担。
- TG 媒体 parse/download、下载上下文、文件流读取、client 不可用分类、换号重试和 alarm 调度：由 `provider/media/telegram_media.py` 承担。
- TikTok 上游 HTTP 响应打开、请求级 httpx client 和释放：由 `provider/media/tiktok_media.py` 承担；不保留单独 TikTok HTTP runtime。
- Playwright/browser 运行时：`app/provider/browser_runtime.py`。
- X cookie 池文件读写、Cookie 文本解析与脱敏：`app/provider/x_cookie_pool.py`。

`provider/media` 可以调用这些 provider 基础设施模块，但不能调用 `app.services`。

service 只保留跨平台公共编排和业务域：

- `media_provider_service.py`：parse/download 编排、Provider 查找、token extra 透传、active guard、限速包装、release、错误映射。
- `media_active_download_service.py`：进程内活跃下载计数。
- `media_download_token_service.py` / `media_resource_token_service.py`：token 签发与验签。
- `media_service.py`：pre-v2 扣费、去重和计费规则，本轮不动。
- `proxy_bandwidth_limit_service.py`：proxy 输出限速。
- `tg_login_service.py`：admin TG 登录流程继续作为登录域 service，改成模块级单例；它单向依赖 `telegram_manager` 获取 manager，`telegram_manager` 和 `TelegramMedia` 不能反向依赖它。

### 4.4 执行停止点

以下情况必须停下来问 Hydra，不允许自行发明绕法：

- 某个 Provider 只有调用 `app.services` 才能完成迁移。
- `TelegramMedia` 看起来需要 `tg_login_service` 才能解析或下载。
- `tg_login_service` 无法在不被 `telegram_manager` 反向持有的前提下完成模块级单例改造。
- 删除旧 service 会导致某个平台可用性下降，需要在“简单边界”和“平台成功率”之间取舍。
- 需要移动 admin 登录域职责，而不是只调整 TG 媒体下载职责。

### Phase 1 · 中性媒体契约层

改动：

- 新增 `backend/src/app/contracts/media_platform.py`：
  - 平台常量。
  - `detect_platform()`。
- 新增 `backend/src/app/contracts/media_download.py`：
  - `MediaDownloadMode`。
  - `MediaDownloadTokenClaims`。
- 新增或调整 `backend/src/app/constants/media_download.py`：

- 删除 `services/media_platform_service.py`，调用方改到中性契约层。
- `media_download_token_service.py`：`PLATFORM_*` 改到 `contracts/media_platform.py`，`MediaDownloadTokenClaims` / `MediaDownloadMode` 定义迁到 `contracts/media_download.py`。

- `base_media.py`：claims 类型 import 改到 `contracts/media_download.py`。

- 平台识别失败和 registry 缺 Provider 的错误口径不变。

### Phase 4 · TikTok proxy 并入 Provider

改动：

- 将 `tiktok_client_service.py` 中仍未迁入的 parse、缓存、SSR、短链解析、下载上下文解析并入 `TikTokMedia`。
- TikTok 上游 HTTP 打开逻辑并入 `provider/media/tiktok_media.py`。
- `TikTokMedia` 每次下载创建本次请求专用 httpx client，随 `StreamDownloadResult.aclose` 释放；不保留进程级 client，不需要 shutdown hook。
- 删除 `provider/tiktok_http.py`。
- `prepare_download_response` / `PreparedTikTokDownload` 是无调用方旧入口，随旧 service 删除，不迁移。
- 删除旧 `tiktok_client_service.py`。

验收：

- `main.py` shutdown 不再 import `app.services.tiktok_client_service`。
- `test_lifespan.py` 不再校验 TikTok HTTP runtime close。
- TikTok parse/download 行为、Range、上游 403 重解析、416 映射保持现有契约。

### Phase 5 · Telegram 媒体 Provider 与账号池边界收口

改动：

- `provider/telegram_manager.py` 承载进程级账号池入口：
  - `ensure_telegram_manager_started()`。
  - `shutdown_telegram_manager()`。
  - `get_discovered_session_count()`。
  - 既有 `AUTH_SESSION_FILENAME`、`RemoveClientResult`、`SessionProcessLock` 等 manager 类型/常量继续从 manager 模块导出。
- 删除旧 TG runtime 门面，不保留上层转调或兼容薄壳。
- `tg_login_service.py` 改为模块级单例 `tg_login_service`：
  - 去掉构造参数中的 `telegram_manager`。
  - 内部按需调用 `telegram_manager.ensure_telegram_manager_started()` 获取 manager。
  - `ensure_started()` 幂等启动后台清理 task。
  - `stop()` 在 shutdown 时先于 `shutdown_telegram_manager()` 执行。
- `TelegramMedia` 只保留：
  - Telegram parse。
  - Telegram download。
  - Telegram 下载上下文解析、client 引用释放、文件流读取。
  - TG client 不可用分类、换号重试和 alarm 调度。
  - Telegram parse 结果展平。
  - Telegram Range 解析。
  - Telegram media error 映射。
- `map_telegram_error()` 迁入 `TelegramMedia` 私有方法或同类私有 helper；`TelegramMedia` 不再从旧 service import。
- admin/internal API 使用 `provider/telegram_manager.py` 获取 manager/session count；admin 登录流程直接使用 `tg_login_service.py` 模块级单例。
- `main.py` shutdown 先停止 admin 登录 service，再关闭 `telegram_manager`。
- `prepare_download_response` / `PreparedTelegramDownload` 是无调用方旧入口，随旧 service 删除，不迁移。
- `parse_range_header` proxy 变体随旧 dead 链删除；现有测试迁移到 `test_telegram_media.py` 覆盖 `TelegramMedia` 的 proxy Range 解析，不保留旧函数。
- 删除旧 `tg_client_service.py`。

验收：

- `telegram_media.py` 不 import `app.services.tg_client_service`。
- `telegram_media.py` 不 import `app.services.tg_login_service`。
- `admin_tg_client.py` 不再调用 `_ensure_manager_started()` 这种私有方法；改用 `telegram_manager.ensure_telegram_manager_started()` 的公开入口。

## 8. 风险与处理

- TG 依赖较多：账号池生命周期只留在 `telegram_manager.py`，媒体请求上下文只留在 `TelegramMedia`，不再新增 runtime 门面。
- `TelegramMedia` 若需要 `tg_login_service` 才能完成 parse/download，必须停下来问 Hydra；默认结论是媒体下载不依赖登录流程 service。
- `tg_login_service` 若无法按模块级单例单向依赖 `telegram_manager`，必须停下来问 Hydra。
- TikTok HTTP client 是请求级资源，只能由 `TikTokMedia` 返回的 stream/aclose 释放，不接 app shutdown。
- direct 平台缓存和 format extra 不能依赖节点本地不可共享状态；否则候选节点下载会失败。
- 测试 monkeypatch 路径会大量变化，必须同步迁移到 provider/runtime 路径。
- 如果迁移后某个平台真实解析失败，优先修 Provider 或 runtime 边界，不恢复旧 service。

## 9. 完成标准

- `provider/media` 与本轮新增媒体 runtime 对 `app.services` 零依赖。
- 旧平台 `*_client_service.py` 全部删除。
- 旧媒体共享 service 按清单迁出或删除。
- Provider 不是薄壳，平台私有逻辑在对应 Provider class 内。
- `TelegramMedia` 不承载 admin 登录、session count、shutdown 这些账号池生命周期能力。
- `telegram_manager.py` 是唯一 TG 账号池生命周期入口，不复制第二套账号池。
- 旧 TG runtime 门面已删除，不保留兼容薄壳。
- `tg_login_service` 是模块级单例，并且只单向依赖 `telegram_manager`。
- `TikTokMedia` 不持有进程级 httpx client；请求级上游 response/client 必须由 `StreamDownloadResult.aclose` 释放。
- `media_provider_service.py` 不新增平台 if。
- 新增平台只需要新增 Provider 文件、registry、测试和站点适配文档。
- 格式、ruff、mypy、媒体相关测试、TG provider/admin 测试通过。
