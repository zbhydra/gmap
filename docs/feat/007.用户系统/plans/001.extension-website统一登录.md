# 001 · extension website 统一登录

> ⚠️ **已被后续方案替代**:本计划的「website 登录页同步插件」形态先演化为 v2 桥(plans/005),又于 2026-09-01 被 v3 浏览器身份(plans/006)整体替代——官网推送与 `POST /auth/extension-token` 均已删除,现行合同见 `@../tech-第三方登录.md` §9。本文仅作历史记录。

## 目标

插件点击登录后统一打开 website 独立登录页。website 已登录时直接同步插件登录态;未登录时复用现有 Google / 邮箱登录。用户直接在官网任意登录入口登录成功时,也同步插件登录态。

## 改动范围

### 后端

1. 通用 `LoginResponse` 不改。website 先完成普通网页登录,extension background 再用 web access token 调 `/api/client/auth/extension-token` 获取插件 token。这里是"已有 website 登录态 → 签发插件 token",不是签到补签;用户网页登录时可能没安装插件,后续安装或点击插件登录仍可同步。
2. 为 extension token 创建独立 token pair,并写入 Redis token ZSet 与用户 session。
3. 新增已登录插件 token 签发接口:

```text
POST /api/client/auth/extension-token
Authorization: Bearer <web_access_token>
```

响应:

```json
{
  "extension_access_token": "...",
  "extension_refresh_token": "...",
  "token_type": "bearer",
  "expires_in": 86400,
  "user": {}
}
```

请求体可选:

```json
{
  "old_extension_access_token": "...",
  "old_extension_refresh_token": "..."
}
```

插件 token 签发接口要求:

- web access token 过期/无效走现有 `get_current_user` 认证失败口径(HTTP 401 / auth 业务错误)。website 自己校验网页登录态时用统一 auth failure 判断清理本地 token 并回到登录 UI;extension background 签发遇到 401 时只放弃写入插件 storage。
- 连续调用每次签发新插件 token。
- 如果 background 带了旧插件 token,后端先解析旧 token 并校验 token type 与字段匹配,再比较旧 token `user_id` 与当前认证用户 `ctx.user_id`;相等才按当前 `ctx.user_id` 的 token ZSet 尝试撤销旧 access/refresh,不相等则跳过撤销。撤销目标必须始终是 `ctx.user_id`,禁止使用旧 token 解码出的 user_id 作为撤销目标。旧 token 解析失败、类型不匹配、过期、已撤销、非当前用户或撤销失败都不阻断新 token 签发,只记录日志。
- 撤销日志只允许记录 user_id / token_type / 失败原因 / 结果,禁止记录 access/refresh token 明文。
- 用户级轻量限流 10 次/5 分钟。

### website

1. 新增英文 `/extension-login` 页面;本阶段不做 `/[lang]/extension-login`,extension 无论当前 UI 语言为何都打开该页。
2. 页面复用现有 Google / 邮箱登录能力。
3. website 本地存在 access token 时先调用账号信息接口校验;有效则展示已登录/同步中状态,认证失败时按统一 auth failure 处理清理本地 token 并显示登录 UI。
4. Google 登录发起时 `return_to` 固定为当前 `/extension-login` 完整 URL。
5. 页面必须处理 `google_login_code` / `google_login_error` / `google_email_verification`,处理后清 URL。
6. 未登录分支完成 Google / 邮箱登录后保存网页登录态,再发出无 token 登录变更信号。
7. 通过 `window.postMessage({ type:"TG_DOWNLOAD_WEB_AUTH_CHANGED" }, window.location.origin)` 发出登录变更信号,不得使用 `"*"`。
8. 已登录态提供"切换账号"入口:清理本地 web access token,回到 Google / Email 登录 UI。
9. 经 `/extension-login` 首次注册的用户,`register_source` 仍按 website 请求记为 `web`;如需区分插件来源,后续通过埋点解决。
10. token 不进入 URL、query、hash、日志或埋点;`google_login_code` 是 Google redirect 的短效一次性 code,允许短暂出现在回跳 URL,消费后清理。
11. 官网首页/下载页等其他登录入口登录成功后,也发出同样的登录变更信号。
12. `/extension-login` 不接触插件 access/refresh token,只使用 website 现有 web access token;页面 CSP 沿用 website 登录页安全口径。

### extension

1. 登录入口改为打开 website `/extension-login` popup 窗口。
2. 不记录原 Telegram tab/window,不生成 nonce。
3. 重复点击登录时直接打开或聚焦现有 `/extension-login` 窗口。
4. 新增官网 content script bridge,manifest matches 包含 `https://telegramdownloadmedia.com/*`、`https://www.telegramdownloadmedia.com/*` 与精确本地开发 origin(如 `http://localhost:4321/*`)。
5. content script 只接受官网 origin、固定 type 合法的页面消息;页面加载时也可主动读取 `homepage_access_token`。
6. content script 从官网 localStorage 读取 `homepage_access_token`,为空则不转发;非官网 origin 消息忽略。
7. background 校验 sender URL 属于官网 origin,读取当前 `auth_access_token` / `auth_refresh_token`,再用 web access token 调插件 token 签发接口。
8. background 接收接口返回的 `extension_access_token` / `extension_refresh_token` / `user`,写入现有 `auth_access_token` / `auth_refresh_token` / `auth_user_info` storage key;禁止新增 extension 专用 auth storage key;若已有不同 user_id,本阶段直接覆盖并刷新为新账号。
9. 签发失败或 storage 写入失败时记录错误;不做 ACK,website 页面不会收到插件写入失败态,用户可从插件重新点击登录或刷新官网页面。
10. 如果消息来源 tab 是 `/extension-login`,成功后关闭该登录窗口;不强制聚焦回原 Telegram tab。

## 安全口径

- 不接受任意域名发来的 token。恶意域名可发送攻击者自己的有效 token,会导致插件登录到攻击者账号,不是简单的"过期重登"。
- 只允许项目官网 origin 的 content script bridge 同步网页登录态。
- website `postMessage` 的 `targetOrigin` 必须钉死为当前官网 origin。
- website 不接触插件 access/refresh token;插件 token 只在 background 签发成功后进入 extension storage。
- 旧插件 token 只由 background 在签发接口请求体中携带给后端,后端只按当前网页登录用户 best-effort 撤销。
- 并发签发可能留下同账号孤立 token,按 access token TTL 自然过期,不做跨调用去重。
- 不做 ACK;同步失败允许用户重新点击登录。
- 不做双端全局登出:website 登出不清插件 storage,插件登出不清 website localStorage。
- 不做 URL token、不做 Cookie 共享、不新增第三方依赖、不新增依赖注入。

## 验收标准

1. website 未登录时,插件点击登录打开 `/extension-login`,用户完成 Google 登录后 website 与插件都显示同一账号。
2. website token 有效时,插件点击登录不再弹 Google / 邮箱登录,直接同步插件登录态并显示成功。
3. 用户直接在官网首页/下载页完成登录后,已安装插件也同步为同一账号。
4. 插件打开的登录窗口同步成功后关闭;不要求自动聚焦回原 Telegram tab。
5. 未安装或禁用插件时,用户在 `/extension-login` 完成 website 登录不报错。
6. 插件保存的 access/refresh token 可正常请求业务接口,access 过期后可通过 refresh 接口续签。
7. website 本地 token 过期时,页面清理本地登录态并回到 Google / 邮箱登录 UI;extension background 签发遇到 401 不改写插件 storage。
8. 非官网 origin、字段 schema 不合法、sender URL 非官网的同名消息都不会改写插件 storage。
9. 连续点击插件登录不会开多个 `/extension-login` 窗口互相覆盖。
10. 插件 token 不出现在 website JS、URL、浏览器历史、console 日志、SLS 埋点;`google_login_code` 消费后会被清理。
11. website 登出后插件仍保持登录;插件登出后 website 仍保持登录;website 后续登录其他账号并同步时覆盖插件账号。
12. 签发新插件 token 时带旧插件 token,同账号旧 token 被尽量撤销;旧 token 撤销失败不影响新账号登录。
13. 跨账号切换只覆盖 extension storage,不得撤销旧 token 所属账号的服务端 token;旧账号服务端 token 按 TTL 自然过期。

## 测试矩阵

后端 API:

- `/api/client/auth/extension-token` 成功返回插件 token,且 access/refresh 都登记到 Redis/session。
- `/api/client/auth/extension-token` 带旧插件 token 时尽量撤销旧 access/refresh;旧 token 无效或撤销失败仍返回新插件 token。
- 旧插件 token 属于其他用户时,解析旧 token 后发现 `user_id != ctx.user_id`,不得撤销对方 token,接口仍返回当前 web 用户的新插件 token。
- 请求体只带 `old_extension_access_token` 或只带 `old_extension_refresh_token` 时,只尝试撤销对应 token。
- 旧 token 字段类型错位时跳过撤销,类型不匹配或撤销失败不阻断新 token。
- web access token 过期或无效时按现有认证失败口径返回,前端用统一 auth failure 判断处理。
- 用户注销或不可登录时返回现有 auth 错误。
- 10 次/5 分钟限流生效。

website:

- `/extension-login` 本地 token 有效时展示成功/同步中状态并发出登录变更信号。
- 本地 token 过期时清理 token 并回到 Google / Email 登录 UI。
- Google redirect 回到 `/extension-login` 后正确处理 `google_login_code`、`google_login_error`、`google_email_verification`,并清理 URL 参数。
- 官网首页/下载页登录成功后也发出登录变更信号。
- `postMessage` 使用当前官网 `targetOrigin`,不使用 `"*"`,插件 token 不进入 website JS/日志/埋点。
- website 登出只清 website 本地 token,不向插件发退出同步。

extension:

- content script 只在官网 match 中注入,非官网 origin 消息被忽略。
- 消息 type/schema 不合法、sender URL 非官网的消息都不会改写 storage。
- content script 能读取官网 `homepage_access_token`,为空时不触发插件 token 签发。
- background 用 web access token 调 `/api/client/auth/extension-token` 成功后才写插件 storage,并在请求体携带当前旧插件 token。
- 成功消息把 `extension_access_token` / `extension_refresh_token` / `user` 写入现有 `auth_access_token` / `auth_refresh_token` / `auth_user_info`。
- 重复点击只聚焦当前 `/extension-login` 窗口。
- 签发或 storage 写入失败时不写半截登录态,用户可重新点击登录或刷新官网页面。
- 插件登出只清 extension storage,不清 website localStorage。

## 风险与回滚

- 风险:插件 token 签发接口必须登记 extension token,否则插件 refresh / 鉴权失败。
- 风险:不做 ACK 会出现网页登录成功但插件未同步的假成功;本阶段接受该简单方案,用户可从插件重新点击登录或刷新官网页面。
- 风险:website 只存 access token,24 小时过期后无法免登录签发插件 token;本阶段接受该限制。
- 风险:统一登录可能把插件从旧账号切到 website 当前账号;本阶段直接覆盖并刷新 UI,不加确认弹窗。
- 风险:website 登出不影响插件登录态;本阶段按双端独立登录处理,用户可在插件里单独退出。
- 风险:跨账号切换和并发签发可能留下旧账号或同账号孤立有效 token;本阶段按现有 token TTL 自然过期兜底。
- 风险:refresh 轮换 30 秒宽限期内旧 refresh 可能短暂可用;本阶段接受宽限期行为。
- 回滚:保留现有邮箱验证码登录入口;隐藏 `/extension-login` 入口与插件打开 website 登录按钮即可回到现状。
