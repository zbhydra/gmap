## 1. 背景与证据

**为什么改**：Maps 插件当前没有任何可用登录入口。007 历史口径的 v2 桥（官网页经 `externally_connectable` 向固定扩展 ID 发 web token）在 TG 线退役后已无实现载体：

- `extension/vite.config.ts:412` `externally_connectable.matches: []`，插件无 `onMessageExternal` 监听；
- `website` 无 `/extension-login`、`/extension-login-v2` 页（仅存 Bing 的 `/extension-login-bing`），`auth.ts:186` `EXTENSION_TARGET_IDS` 为空数组；
- 后端 `POST /auth/extension-token`（`auth_client.py:527`）生产代码零调用方（仅剩一份 real 集成测试引用，随端点一并删除）；
- 插件 popup 无登录按钮，`auth.login` / `LOGIN_NOT_AVAILABLE`（`core/constants/i18n.ts:36`）为无消费死文案。

参考项目 Extension Pro 的 v3 方案用 `chrome.identity.launchWebAuthFlow` + PKCE(S256) + 一次性 code 替代 v2：不登记扩展 ID、不需要 `externally_connectable`、web token 不进任何消息通道或 URL，并已在对方仓库完成三端验收。本计划将该流程移植到本仓库三端，**并同时迁移 Bing 插件、删除其 v2 桥**。

**Bing 侧现状**（v2 桥唯一真实使用方，未上架商店、无已发布旧包）：

- 官网 `/extension-login-bing` 桥接页登录后经 `externally_connectable` 向固定 ID `pgcpggcfmfdmobpheojngndpcmnkibmm` 推送 web token（`website/src/scripts/homepage/auth.ts:188-194,279-304`）；
- 插件 `WebsiteAuthBridge`（`extension-bing/src/background/services/WebsiteAuthBridge.ts`，`onMessageExternal` + origin 白名单）收编 web token 直存（`authStore.applyWebsiteToken`，`authStore.ts:166-195`），不调换票端点；
- manifest 携带固定 `key` 与 `externally_connectable`（`extension-bing/vite.config.ts:255-257,296-298`），permissions 仅 `storage`；
- **插件内无任何登录入口**（popup 无账号区、面板徽标仅登录后显示）——v2 是「官网推送」模式无需插件内入口，v3 是「插件发起」模式，**必须新增登录入口**（016「popup 不设账号区」拍板的前提随 v2 桥删除而失效，见 §2）。

**gmap 侧已具备的底座**（v3 直接复用，不新建）：

- 插件 manifest 已含 `identity` 权限（`extension/vite.config.ts:342`，A10 HubSpot 授权引入）；
- 后端插件 token 签发链完整：限流器 `_extension_token_limiter`、`_ensure_user_can_login`、旧 token best-effort 撤销、`user_auth_service.issue_registered_tokens_for_user`；
- 一次性 code 的既有同构机制：`google_redirect_login_service`（哈希存 Redis + 一次性消费）；
- website 登录能力：`AuthModal.astro`（Google 主路径 + 邮箱验证码）+ `homepage/auth.ts`（`getStoredAccessToken` / 三种登录函数 / Google redirect 收尾），Bing 桥页已验证可复用；
- 插件 401 刷新拦截器与 `authStore` 被动恢复已就位。

## 2. 目标与非目标

**目标**：

1. Maps 与 Bing 两个插件统一经 v3 browser identity 登录：插件内登录入口 → background `launchWebAuthFlow` → 官网确认页 → 一次性 code exchange → 插件持有独立 token 对（沿用现有三键 storage 与刷新机制）。两插件共用同一官网页 `/extension-login`。
2. Maps：登录后配额归属自动从 device 切到 user（统一 usage 服务双轨已支持——登录 MySQL 流水/匿名 Redis 计数，2026-09-01 起为 `usage_service` 门面；请求头拦截器自动带 Bearer，无需改动）；Bing：登录后订阅联动（FREE/PRO 门控）照常工作。
3. **删净 v2 桥全部残留**：后端 `/extension-token` 端点与 real 测试、Maps 侧 v2 死常量/死文案、Bing 侧 `WebsiteAuthBridge`/官网桥接页/固定 key/`externally_connectable`/推送常量、过时文档口径。

**非目标**：

- 不引入强制登录墙：Maps 免登录可用、配额按 device 不变（013 已拍板差异 #1）；Bing 免登录匿名免费档（20 条截断）不变（016 已拍板差异）。
- 不做 license key、插件内 OAuth 表单、订阅门控变更（Maps Pro 徽章门控仍待 C2；Bing FREE/PRO 逻辑原样保留）。
- 不改 website 首页登录体验本身（AuthModal 原样复用）。

**拍板变更**：016 feat「Popup 不设账号区」基于 v2 官网推送模式（插件内无需入口）；v3 由插件发起登录，必须提供插件内入口。Bing 的登录入口为 popup `Sign in` 按钮 + 面板未登录态 `Sign in` 按钮（登录后该位置恢复显示 FREE/PRO 徽标），两入口走同一 background RPC。

## 3. 协议合同（v3 browser identity）

两插件（Maps / Bing）共用同一套合同与同一官网页 `/extension-login`——合同对插件类型无耦合（回调 host 为运行时 `chromiumapp.org` 域名，入口校验通用）。

时序（`E`=插件 background，`W`=官网页，`B`=后端）：

```text
E: 生成 verifier/challenge(S256) → launchWebAuthFlow 打开
W: {WEBSITE}/extension-login/?redirect_uri=<chromiumapp回调>&code_challenge=<43字符>
W: 入口校验 redirect_uri + code_challenge，非法→错误文案终止
W: 已登录→账号确认卡；未登录→AuthModal 登录（Google 主路径 / 邮箱验证码）
W: 用户点 Continue → POST /api/client/auth/extension-login/code（Bearer）→ {code, expires_in:60}
W: location.replace(<redirect_uri>#code=<code>) → 浏览器自动关窗
E: launchWebAuthFlow resolve → 解析 fragment code
E: POST /api/client/auth/extension-login/exchange（无 Bearer；code+verifier+旧插件token可选）
B: Lua 原子 GET+DEL 消费 code → S256 比对 challenge → 按 code 内 user_id 签发插件 token 对
E: 校验响应合同 → 快照比对 → 原子写 chrome.storage 三键 → popup 感知刷新
```

关键约定（与参考实现一致）：

- **PKCE**：verifier = 32 字节随机 → Base64URL（43 字符）；challenge = BASE64URL(SHA256(verifier))；固定 S256，不传算法参数。无 `state`（RFC 9700 §2.1：PKCE 即 public client 的 CSRF 防护）。
- **回调**：`chrome.identity.getRedirectURL('extension-login')` → `https://<32位小写a-p>.chromiumapp.org/extension-login`；code 只走 URL fragment（不进 server 日志 / referer）。
- **code**：`secrets.token_urlsafe(32)`；Redis key 只存 `sha256(code)` 摘要；value JSON `{user_id, code_challenge, created_at}`；TTL 60 秒；Lua 原子 GET+DEL，**先消费后验 challenge**——code 不存在/过期/已消费/verifier 不匹配统一 `AUTH_INVALID_CREDENTIALS`，无尝试计数与恢复。
- **token**：Website token 与插件 token 完全独立（同 user_id 下不同 session，各自 jti 与白名单条目）；官网回调 URL 不含任何一种 token。
- **安全边界（接受）**：public client，不登记扩展 ID、无 `externally_connectable`——任何扩展可为自己的回调发起登录，但只能拿到绑定其自身 verifier 的一次性 code，账号交接必须由用户在官网显式点 Continue 确认。

## 4. 三端改动

### 4.1 backend

**新增** `services/extension_login_code_service.py`（风格对齐 `google_redirect_login_service`：`build_redis_key` + 摘要 key + 模块级实例，无构造注入）：

- `create_code(user_id, code_challenge) -> str`：生成 code、哈希落 Redis（`ex=60`）。
- `consume_code(code, code_verifier) -> int`：Lua 原子消费 + `_create_s256_challenge` 与存储值 `hmac.compare_digest`；Redis 读写失败 fail-closed（`INTERNAL_SERVER_ERROR`，不签发）。

**修改** `api/client/auth_client.py`：

- 将 `_enforce_extension_token_rate_limit`、`_best_effort_revoke_old_extension_token(s)`、`_create_extension_token_response` 的 `UserContext` 参数收敛为显式 `user_id` / `ip` / `client_product`（v3 exchange 无 Bearer，无 UserContext；禁止构造假 UserContext）。
- 新增 `POST /auth/extension-login/code`：`Depends(get_current_user)` Bearer → challenge 格式校验（`^[A-Za-z0-9_-]{43}$`）→ `_ensure_user_can_login` → 共享限流（`extension_token_issue`，10 次/300 秒 per user）→ `create_code`；响应 `{code, expires_in: 60}`。
- 新增 `POST /auth/extension-login/exchange`：无 Bearer → verifier 格式校验（`^[A-Za-z0-9._~-]{43,128}$`）→ `consume_code` 得权威 `user_id` → 旧插件 token best-effort 撤销 → 签发链 → 响应同 `ExtensionTokenResponse` 结构。
- **删除** `POST /extension-token`（v2）：生产代码零调用方，且本仓库无已发布旧包兼容负担（参考项目保留 v2 是有其已发布旧包在用，gmap 没有这个约束，按「删净被替代旧方案」处理）。`ExtensionTokenRequest` 保留为 exchange 请求的 old-token 字段基类。同步重写模块 docstring 中「Website 登录后同步插件」的 v2 流程描述（`auth_client.py:16-27`）。

**新增 schema**（`schemas/client_user_schema.py`）：issue 请求（仅 `code_challenge`）/ 响应（`code` + `expires_in`）；exchange 请求（继承 old-token 字段 + `code` + `code_verifier`）。

**测试**：删除 `tests/integration/real/api/client/test_auth_extension_token_real.py`（v2 端点专用，由新用例替代覆盖）；新增 real 集成用例覆盖 ① Bearer issue → exchange → 插件 token 可访问 `/auth/me`；② 错误 verifier 消费后，同 code + 正确 verifier 仍失败（证明先消费后校验）。不建 v2 兼容矩阵。

### 4.3 extension（Maps 插件）

**background** 新增 `openExtensionLogin` RPC（登录 owner 唯一入口；`launchWebAuthFlow` 必须在 background，popup 生命周期不覆盖登录窗口）：

1. 生成 verifier/challenge，构造 `getRedirectURL('extension-login')` 与官网登录 URL；
2. `launchWebAuthFlow({ url, interactive: true })`；
3. resolve 后解析 fragment 的 `code`，无 code → `{opened:false}`；
4. exchange（携带当前旧插件 token 供 best-effort 撤销）→ 校验响应合同（token 对 + 数字 `user_id`）；
5. **快照比对提交**：exchange 前读三键快照，提交前重读比对（access+refresh+user 三者全等才写），不一致（如期间用户已在 popup 登出）→ 放弃写入返回 `{opened:false}`；gmap 登录入口唯一（本 RPC），不移植参考项目的串行 mutation 队列。已知并接受的反向窗口：提交后若旧会话的 in-flight refresh（各 context 拦截器 per-context 单飞）晚于提交写回，会以旧账号覆盖新登录对——概率低、用户重新登录即自行恢复，符合容错轴，不为它做跨 context 刷新改造；
6. 任何失败（关窗、参数、exchange、提交冲突）统一捕获返回 `{opened:false}`，不写半截态、不重试、不清原登录态。

`authApi` 新增 `applyExtensionLogin(tokenResponse)`（三键写入 + 快照比对条件提交）；读/清函数沿用。

**popup** 账号区（现有 Guest + usage 条位置）：

- 未登录：`Sign in` 按钮 → RPC `openExtensionLogin`，发起后按钮进入 loading；RPC 返回 `{opened:false}` 或触发默认 30 秒 RPC 超时均静默复位按钮态（完整登录常态超 30 秒，不为其调大超时）——**登录最终结果一律以 storage.onChanged 为准**，不依赖 RPC 返回值。
- 已登录：显示 `displayName` + `Sign out`（沿用 `authStore.logout`）。
- popup 注册 `chrome.storage.onChanged`（auth 三键）监听：登录在 background 完成，popup 若保持打开需即时刷新 authStore（`initialize` 重跑或直接应用新值），**并同时重拉 usage**（复用 `refreshUsage`，登录后用量切账号归属）。
- i18n：复用已有 `auth.login` / `auth.logout` 文案，删除 `LOGIN_NOT_AVAILABLE` 死常量。

**manifest / 清理**：无新增权限（`identity` 已有）。删除 vite.config 的 `externally_connectable` 空对象与 `TODO(maps)` 注释（v3 决策：不恢复白名单），以及整条为其服务的死派生链：`externallyConnectableMatches`（接口字段 `:89-90`、构造 `:208`、返回 `:217`，manifest 用的是字面空数组）、`toMatchPattern`（`:174-176`）、`resolveRuntimeWebsiteAuthOrigins`（`:182-187`）、`PROD_WWW_WEBSITE_BASE_URL`/`PROD_WWW_WEBSITE_ORIGIN`（`:40,51`）；`DEFAULT_PROD/DEV_WEBSITE_BASE_URL` 保留（`homepage_url` 与 `__WEBSITE_BASE_URL__` define 仍依赖）。同时删除 `WEBSITE_AUTH_ORIGINS`、`WEBSITE.PRODUCTION_BASE_URL`/`WWW_BASE_URL`（TG 残留域名，`config.ts:77-79`，仅被 `WEBSITE_AUTH_ORIGINS` 构造引用；`PRICING_PATH` 保留）、`AUTH_EXTENSION_TOKEN` 死常量、`LOGIN_NOT_AVAILABLE` 死文案（v3 端点常量另立新名）。

## 5. 用户可见行为（验收基准）

1. popup 未登录显示 Guest + 用量条 + `Sign in`；点击后弹出官网登录窗口。
2. 官网页未登录：AuthModal（Google 主按钮 + `Continue with email`）；登录成功进入账号确认卡。
3. 官网页已登录（或刚登录完）：显示账号确认卡（头像/姓名/邮箱），**必须点 Continue** 才签发；`Use another account` 清 website 会话回到 AuthModal。
4. Continue 后窗口自动关闭，popup 变为已登录（displayName + Sign out），无需重开 popup。
5. 用户直接关闭登录窗口 / 网络失败 / 参数非法：插件保持原状（未登录则仍未登录），可再次点击登录。
6. 登录后配额按账号计：`/maps/usage` 以 `u:{user_id}` 归属（popup 与面板用量条数据源不变）。
7. 未登录用户行为零回归：免登录采集、device 配额、匿名 upgrade 流程不受影响。
8. 登出：清插件三键 + 撤销服务端当前 access token（现有 `authStore.logout` 行为）。
9. 同一 code 重放 exchange 失败（一次性）；错误 verifier 后同 code 正确 verifier 也失败。
10. Bing：popup 与面板两处 `Sign in` 均可发起登录，流程与 Maps 一致；登录后面板徽标显示 FREE/PRO，订阅门控按登录态生效（Pro 无上限 / 免费 20 条截断）。
11. Bing 匿名行为零回归：未登录免费档可用、Upgrade 引导正常、匿名会话零账号/订阅请求。
12. 两插件先后经同一官网页登录互不干扰（各自独立 token 对、各自 session）。
