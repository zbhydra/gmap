## 1 · 目标

把官网 ↔ 扩展的登录桥接从「content script + postMessage 开放信道」迁移到 `externally_connectable` 封闭信道：

- 删除 `websiteAuthBridge.ts`（198 行）与 manifest 中的官网域 content script 注入；
- 官网域从扩展权限详情页消失（externally_connectable 不产生权限警告、不授予 host access）；
- 「返回 Telegram」简化为：background 根据 `sender.tab.id` 关闭登录页 + 聚焦第一个 `web.telegram.org` tab；页面 `window.close()` 仅兜底。

## 2 · 非目标

- 不改后端（`/api/client/auth/extension-token` 复用）；
- 不动旧页面 `/extension-login` 与 postMessage 协议（旧扩展依赖，原样保留到自然消亡）；
- 不把 `onMessageExternal` 塞进自研 RPC 框架（对端是网页，非扩展上下文；独立轻量 handler）；
- 不统一既有 8 处商店链接硬编码（范围外）；
- 不做「聚焦已打开的登录页」：重复点击登录按钮直接再开新页，旧页由用户自理。

## 3 · 旧版兼容（页面级分离，无双协议探测）

**证据**：已发布旧扩展（≤1.3.0）的二进制写死 `EXTENSION_LOGIN_PATH = /extension-login`，且其 bridge 注入官网全域，无法召回升级。

**方案**（用户指定）：

| 页面 | 协议 | 服务的扩展 |
|---|---|---|
| `/extension-login`（不动） | postMessage + 旧扩展 bridge | 已发布旧扩展 |
| `/extension-login-v2/`（新增） | `chrome.runtime.sendMessage` | 新扩展 |

新版 `buildExtensionLoginUrl()` 指向 v2 路径，天然分流；无双协议探测、无版本协商。旧页面文件与旧协议常量零改动；唯一共享点 `notifyWebAuthChanged()` 为纯追加一条 external 发送（非双写——两协议独立收发，无状态需同步维护）。

**边界推演**：

- 旧扩展手输打开 v2 页：旧 bridge 注入但 v2 不发 postMessage → 不同步；旧扩展点登录按钮仍走旧页。无害。
- 新扩展手输打开旧页：`notifyWebAuthChanged()` 追加的 `sendMessage` 会实际完成同步，但旧页 `waitForExtensionTokenExchange`（extension-login.astro:450，800ms 重试 + 15s 超时）等的是 postMessage 回执 → **页面显示超时错误而 token 已同步**。报错误导但自愈（用户回到扩展即见已登录）；仅手输 URL 触发。接受。
- Google redirect 回跳后的 tab 可能不满足 script-closable 条件：background 仍可用 `sender.tab.id` 关闭；若 tab 已被用户关闭，忽略 `tabs.remove` 错误。
- `sendMessage` 目标 id 未安装：**不抛异常**，Chrome 只设置 `chrome.runtime.lastError` 并调用 callback——必须在 callback 内读取 `lastError` 转为错误分支（codex 复审项），记录用 website 侧现有机制（`logGoogleAuthStage('error', ...)` 或 `console.error`——website/website-shared 无 extension 的 `logger`，codex 复审项）后显示「未检测到扩展」。接受。

## 4 · extensionId 分发

- **生产 id 白名单**：正式 id `lflkobgaibapekhjnfhkaeagdnojjnla`（源自 website 现有商店链接）+ 上线前测试 id `cknimihpjagocmakbkplpjdcgjlbnkec`，常量统一放在 `website-shared`。
- **安全边界（codex 审核高危项）**：生产 `?ext=` 仅命中上述白名单时生效，其他值回退正式 id。否则攻击者构造 `官网/extension-login-v2/?ext=<恶意扩展id>` 即可让受害者把 `homepage_access_token` 发给任意自行声明了 `externally_connectable.matches` 的恶意扩展（[官方 messaging 文档](https://developer.chrome.com/docs/extensions/develop/concepts/messaging#external-webpage)：网页可向指定 extension ID 发消息）。
- **dev**：`buildExtensionLoginUrl()` 附 `?ext=<chrome.runtime.id>`，localhost/127.0.0.1 接受任意 query id（dev unpacked id 随路径变化）。
- `notifyWebAuthChanged()`（官网任意页登录钩子）只向正式 id 发——dev 场景不同步，走 v2 页手动链路。接受。

## 6 · 关键流程（v2 主链路）

```
popup 未登录 → tabs.create(官网/extension-login-v2?ext=<id>)
用户登录 → v2 页 sendMessage(AUTH_CHANGED, token)
→ background 校验 sender.origin → 后端换 extension token → 存储 → sendResponse(ok)
→ v2 页显示成功 + 返回按钮
点击返回 → sendMessage(RETURN)；延迟 window.close() 兜底
→ background query 第一个 web.telegram.org tab → 聚焦 + tabs.remove(sender.tab.id)
```

## 7 · 验收标准

1. 新扩展 manifest 无官网域 content script；权限详情页不再显示 telegramdownloadmedia.com。
2. v2 登录后扩展登录态同步；官网任意页登录同样同步（正式 id）。
3. 「返回 Telegram」：background 关闭登录页 + 聚焦第一个 telegram tab（多开取第一个）；页面 `window.close()` 仅兜底。
4. 旧扩展（1.3.0）走旧页全流程不受影响。
5. `pnpm check` + 双端 build 通过。

## 8 · 验证方式

- extension：单测 + `pnpm check` + build；加载 dist 手动 e2e（登录同步、返回、旧页回归）。
- website：`pnpm build` + 本地 4321 走 dev 链路（`?ext=` 注入 dev id）。
- 旧版回归：用 1.3.0 的 zip 或商店版并装旧扩展验证旧页桥接。

## 9 · 已知未知 / 风险

- `externally_connectable` 变更在扩展更新时不触发权限提示（官方语义），预期无感升级。
- 旧扩展升级到新版后，若用户停留在旧登录页（升级前打开）：`notifyWebAuthChanged` 的追加发送**可能已完成同步**，但旧页仍会超时报错；用户重新点登录按钮走 v2 即恢复。接受。
- Chrome 对 `externally_connectable.matches` 不接受 `<all_urls>`；本项目为具体域名，不受影响。
