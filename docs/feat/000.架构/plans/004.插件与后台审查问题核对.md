## 3. Pro 补全接口缺少服务端权限门禁

**原问题与证据：** [enrich_maps_businesses](../../../../backend/src/app/api/client/maps_client.py) 使用 `get_current_user_optional`，未检查调用者订阅。传入格式合法的设备标识、没有 Bearer token 时，[身份依赖](../../../../backend/src/app/api/user_dependencies.py) 可返回 `user_id=0`，后续仍进入抓取流程。设备标识仅校验字符与长度，不能证明登录或订阅。插件产品将 Email/社媒补全列为付费权益。

**触发与影响：** 调用者绕过插件 UI 直接请求接口，即可匿名使用补全能力并消耗服务端抓取资源。单批数量和共享并发限制不能替代账号权限检查。

**处理结论（2026-10-29）：** 服务端补全需要登录并持有有效插件订阅，任意有效付费档位均可；不新增请求级限流。保留单批、共享并发、超时与 SSRF 边界，以及“补全不重复扣采集额度”的计量合同。正式合同见[官网联系方式采集 §3](../../014.Maps云端/tech-官网联系方式采集.md#3-本项目编排)。

**实施范围：** 共享 API 复用严格登录依赖及现有有效订阅 owner，在 provider 与缓存前拒绝无权益请求；Google 完成边沿补充插件权益判断，Bing 沿用现有订阅门控。双插件 HTTP 补全通道删除 `requireAuth:false`，启用既有 Bearer 注入；Google 设置页文案仅收紧 Email/社媒补全，不改变其他导出字段的开放规则。

**验收：** 匿名、无有效插件订阅（含到期、仅有 Online/API 订阅）的账号不能抓取或取得共享缓存结果；有效插件订阅可补全，缓存与 SSRF 行为保持；补全不产生采集用量流水。

## 4. 迟到的刷新响应覆盖新账号凭据

**原问题与证据：** 审查基线中，[Google 插件刷新拦截器](../../../../extension/src/core/api/client/interceptors.ts) 与 [Bing 插件刷新拦截器](../../../../extension-bing/src/core/api/client/interceptors.ts) 的 `parseRefreshResponse` 无条件写入新 token，未核对请求发起时的会话是否仍有效，access/refresh token 还分两次写入。

**触发与影响：** 真实可达链路为“A 的后台认证请求触发刷新并挂起 → popup 退出 A → 官网确认登录 B → A 的刷新响应返回”。旧实现会把 B 的 token 覆盖为 A 的新 token，并重试原请求；用户资料可能暂时仍为 B，随后界面可因存储监听重新验活或清态。若 A 的新 token 有效，后续请求按 A 执行；失效则认证失败。仅退出时，迟到响应也可能重新写入旧凭据。

**处理结论（2026-10-29）：** 双插件由 background 统一执行认证 HTTP、刷新、登录和退出凭据提交，正式合同见[插件侧认证行为](../../007.用户系统/tech-第三方登录.md#95-插件侧行为maps--bing-同构)。popup 只保留展示状态，通过限定扩展页调用的 `getAuthState` / `logout` RPC 校验和退出；RPC 不返回 token。

**改动：** 两端 `core/api/auth/session.ts` 统一快照比对与存储提交：登录比对三键，刷新、资料回写与认证失败清理比对请求实际使用的 token 对。短提交队列只覆盖存储操作，HTTP 不进入队列；刷新成对写 token。退出在同一队列项内读取当前 access token 并删除三键，再在队列外尽力撤销实际删除的 access token；退出请求不触发刷新，popup 在 RPC 完成后重新读取当前后台状态。HTTP 重试前继续核对原请求快照，会话已变时拒绝旧请求并保留当前会话。Bing 原业务 store 继续管理 background 的订阅缓存。

**验证结果（2026-10-29）：**

- 首轮双插件分别执行 `pnpm exec vitest run tests/integration/auth-session-rpc.spec.ts tests/integration/enrich-rpc.spec.ts tests/unit/http-interceptors.spec.ts tests/unit/popup-toast.spec.ts`，各 52 项通过，无 skip。认证集成穿过 popup store、生成 RPC 客户端、transport、serve、background handler、真实登录 owner、HTTP 客户端与认证存储提交，只替换 Chrome API 和外部 HTTP 出口；覆盖刷新挂起时正常 popup 退出再登录 B、仅退出、旧刷新认证失败、旧资料回写、普通双 401 单飞、等待重试期间换号及认证 RPC 权限。

## 6. Firefox 登录与扩展页权限不兼容

**原问题与证据：** [inferChromeCaller](../../../../extension/src/core/rpc/serve.ts) 只用 `chrome-extension://` 判断扩展页。以 Firefox 的 `moz-extension://` popup sender 调用登录方法，隔离复现返回 `UNAUTHORIZED`，handler 未执行；批量管理方法同样只允许 popup。另有[官网登录页](../../../../website/src/components/pages/ExtensionLoginPage.astro) 的 `REDIRECT_URI_HOST_PATTERN` 只接受 Chromium 回调域名。

**触发与影响：** 已提供分发产物的 Firefox 插件无法正常完成登录，批量 Dashboard 的受限 RPC 也会失败。删除 EventRPC 未改变这两个判断。

**处理结论（2026-10-29）：** Google 插件使用浏览器提供的本扩展根 URL 识别扩展页；官网登录确认页严格增加 Firefox 官方身份回调域。正式合同分别见[插件 RPC 权限](../tech-插件RPC.md#2-请求权限与错误)与[统一登录回调](../../007.用户系统/tech-第三方登录.md#92-pkce-与回调)。

**改动：** `inferChromeCaller()` 改用 `chrome.runtime.getURL('')`，保持浏览器 sender 推导和逐方法调用方限制；确认页保留原有入口校验，只扩充官方回调 host 形状。既有 `getRedirectURL('extension-login')`、PKCE 与一次性 code 交换流程不变。

## 12. 客户端 IP 信任边界
