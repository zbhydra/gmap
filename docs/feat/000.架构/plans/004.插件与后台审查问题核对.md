## 1. 支付回调失败确认与补偿范围

**原问题：** 审查基线中，`PaymentProcessingError(category=retryable)` 经错误中间件处理仍返回 HTTP 200、业务码 500；[履约补偿](../../../../backend/src/app/crons/task/order_fulfillment.py) 只扫描 `PAID + PENDING`。渠道已扣款但本地付款状态落库前失败时，通知被确认接收，订单却未进入补偿范围。

**处理结论（2026-10-29）：** 复用既有分类，由渠道负责重投。正式应答合同已同步至[支付与履约 §8.1](../../004.订单系统/tech-支付与履约.md#81-失败分类与恢复边界)。

**改动：** [错误中间件](../../../../backend/src/app/middleware/error_handling.py) 仅将支付回调中的 `retryable` 映射为 HTTP 500；[ResponseUtils.error](../../../../backend/src/app/utils/response.py) 尊重显式 HTTP 状态。明确拒绝、结果不明及成功重复通知仍按既定应答处理。

**验收：** 以下命令在 `backend/` 执行，3 项测试通过、无跳过；真实 MySQL/Redis 与应用调用链参与验证，仅 PayPal HTTP 出口使用可控响应。覆盖回调临时故障返回 500、明确拒绝与结果不明返回 200、客户端支付接口仍返回业务错误 200，以及重复通知不重复履约。

```bash
uv run --no-sync pytest tests/integration/real/api/client/test_subscription_order_real.py::test_real_paypal_one_time_return_fulfills_once_without_public_webhook tests/integration/real/middleware/test_error_handling_real.py::test_real_invalid_token_uses_common_response_envelope tests/integration/real/middleware/test_error_handling_real.py::test_real_request_validation_failure_uses_common_response_envelope -rs --tb=short
```

受影响 Python 文件通过 black、ruff、mypy；`uv build --wheel --offline --out-dir .cache/payment-callback-build` 成功。独立进程以隔离节点名和临时端口启动真实 Uvicorn，完整 lifespan 启停通过，`GET /api/system/health` 返回 HTTP 200、`healthy`。未进行 PayPal 公网真实重投联调。

## 2. 补全缓存归属与抓取网址不一致

**事实与证据：** [MapsEnrichProvider](../../../../backend/src/app/provider/maps_enrich.py) 的 `_derive_business_key` 优先使用请求中的 `domain`，而 `_resolve_enrich_target` 优先使用 `website` 决定抓取地址。输入 `domain=victim.example`、`website=https://attacker.example/` 时，解析结果为前者的缓存键与后者的抓取 URL；`_enrich_site` 随后按该缓存键读写结果。

**触发与影响：** 目标缓存未命中时，调用者可让自有网站的联系方式写入其他商家的缓存。缓存由双插件共用，错误结果可持续到缓存过期；现有 TTL 由 [maps_enrich 常量](../../../../backend/src/app/constants/maps_enrich.py) 定义。当前 Online/API 使用独立的 Collector 补全缓存，不属于本项已确认影响范围。

**修复方向：** 缓存归属从规范化后的实际抓取 URL 推导，客户端不能独立指定其他域名的缓存键。

**验收：** 使用不同域名构造上述输入，确认不会写入或命中受害域名的结果；正常同目标请求仍能复用缓存。使用隔离测试域名与可清理的缓存键。

## 3. Pro 补全接口缺少服务端权限门禁

**事实与证据：** [enrich_maps_businesses](../../../../backend/src/app/api/client/maps_client.py) 使用 `get_current_user_optional`，未检查调用者订阅，且没有请求级限流。传入合法设备 UUID、没有 Bearer token 时，[身份依赖](../../../../backend/src/app/api/user_dependencies.py) 可返回 `user_id=0`，后续仍进入抓取流程。插件产品将 Email/社媒补全列为 [Pro 字段](../../013.Maps插件/feat.md)。

**触发与影响：** 调用者绕过插件 UI 直接请求接口，即可匿名使用补全能力并消耗服务端抓取资源。单批数量和共享并发限制不能替代账号权限检查。

**修复方向：** 在服务端入口检查登录与有效插件套餐，并使用现有限流能力约束调用。保留“补全不重复扣采集额度”的既定计量合同。

**验收：** 匿名与免费账号不能触发实际补全；有效付费账号可正常补全；失败与限流响应不增加重复扣量。

## 4. 迟到的刷新响应覆盖新账号凭据

**事实与证据：** [Google 插件刷新拦截器](../../../../extension/src/core/api/client/interceptors.ts) 与 [Bing 插件刷新拦截器](../../../../extension-bing/src/core/api/client/interceptors.ts) 的 `parseRefreshResponse` 无条件写入新 token，未核对请求发起时的会话是否仍有效，access/refresh token 还分两次写入。

**触发与影响：** 已隔离复现“A 发起刷新 → 登录 B → A 刷新响应返回”：最终用户信息为 B，token 属于 A，原请求还会重试。后续请求可能归入错误账号；退出期间的迟到响应也存在写回旧凭据的风险。

**修复方向：** 登录、刷新和退出由 background 统一管理；响应只能提交到仍匹配的会话，token 对一次写入。双插件一起修复。

**验收：** 在刷新请求未返回时换号或退出，旧响应不得改变新会话或恢复已退出的凭据；普通刷新与并发请求去重保持可用。

## 6. Firefox 登录与扩展页权限不兼容

**事实与证据：** [inferChromeCaller](../../../../extension/src/core/rpc/serve.ts) 只用 `chrome-extension://` 判断扩展页。以 Firefox 的 `moz-extension://` popup sender 调用登录方法，隔离复现返回 `UNAUTHORIZED`，handler 未执行；批量管理方法同样只允许 popup。另有[官网登录页](../../../../website/src/components/pages/ExtensionLoginPage.astro) 的 `REDIRECT_URI_HOST_PATTERN` 只接受 Chromium 回调域名。

**触发与影响：** 已提供分发产物的 Firefox 插件无法正常完成登录，批量 Dashboard 的受限 RPC 也会失败。删除 EventRPC 未改变这两个判断。

**修复方向：** 使用浏览器提供的扩展根 URL 识别扩展页，并为 Firefox 官方身份回调补齐严格校验。

**验收：** 在真实 Firefox 临时加载产物中验证 popup 登录、官网回跳与批量任务管理；非法回调域名仍被拒绝。

## 7. 批量任务旧回报被当作当前执行

**事实与证据：** [reduceBulkEvent](../../../../extension/src/background/batch/machine.ts) 的 `item-done` / `item-progress` 只匹配任务 ID、条目下标和运行状态；[事件类型](../../../../extension/src/background/batch/types.ts) 不携带本次执行标识。[控制器](../../../../extension/src/background/batch/controller.ts) 接收消息后直接转换为这类事件。

**触发与影响：** 同一条目重试后，任务 ID 与下标保持不变。已隔离复现：旧页 101 超时后启动重试页 202，旧页完成消息迟到，状态机将条目标为完成并要求关闭 202，导致新执行被提前结束。

**修复方向：** 每次启动生成独立执行标识，工作页进度和完成回报必须匹配当前执行。

**验收：** 重试、暂停后续跑及启动回执丢失后的恢复均能拒绝旧执行消息；当前工作页的正常消息仍能推进任务。

## 8. 合法批量任务状态超过 RPC 大小限制

**事实与证据：** [BULK_LIMITS](../../../../extension/src/background/batch/types.ts) 允许 150 个任务、每个 500 条目；[METHOD_RESPONSE_LIMITS](../../../../extension/src/background/background-register.ts) 对批量状态及命令响应限制为 8 MiB。隔离复现使用普通约 50 字符关键词，单次创建参数约 27 KB，完整状态为 9,463,973 字节，`getBulkState` 返回 `PAYLOAD_TOO_LARGE`。

**触发与影响：** [Dashboard.refreshState](../../../../extension/src/dashboard/App.vue) 无法取得合法历史状态。命令响应同样返回全部状态，而[控制器](../../../../extension/src/background/batch/controller.ts) 在生成响应前已经保存变更，可能出现操作已落盘、界面却收到失败的情况。

**修复方向：** 任务列表只返回摘要，详情按任务读取；命令响应只返回必要结果，不重复携带全部历史条目。

**验收：** 在声明的任务与条目上限下，重新打开 Dashboard、读取详情、启动、停止和删除均可完成，成功操作不因响应大小转成失败。

## 9. 后台邮箱筛订单截断用户集合

**事实与证据：** [admin_orders.\_resolve_filter_user_ids](../../../../backend/src/app/api/admin/admin_orders.py) 先调用 `user_lists(email_like=..., limit=1000)`，再将这批用户 ID 交给订单查询。

**触发与影响：** 邮箱筛选如 `@gmail.com` 命中超过 1,000 个用户时，其余用户的订单不会进入列表或总数。若同时指定的用户 ID 不在前 1,000 个结果内，即使邮箱匹配也会返回空结果。

**修复方向：** 将邮箱条件通过 JOIN 下推至订单查询，列表和计数共用过滤条件。

**验收：** 筛选命中超过 1,000 个用户时仍能查询完整订单与正确总数；同时指定用户 ID 与邮箱条件时正确取交集。

## 10. CSV 导出未处理公式注入

**事实与证据：** [Google CSV](../../../../extension/src/sites/maps/content/export/csvText.ts) 的 `escapeCsvCell`、[Bing CSV](../../../../extension-bing/src/sites/bing/content/export/csvText.ts) 与[云端 CSV](../../../../backend/src/app/services/export_file_service.py) 的 `project_gmap_csv` 只处理 CSV 格式。隔离复现中，文本 `=1+1` 原样进入 CSV 单元格。

**触发与影响：** 商家名称、评论等来自第三方的文本若带公式前缀，用户在会解释公式的表格软件中打开 CSV 时，可能执行公式。现有复现证明输出未中和公式，尚未实测具体表格软件的执行行为。

**修复方向：** 在最终 CSV 输出边界统一处理文本字段的公式前缀，保留普通文本、电话号码和数值字段的正常使用。

**验收：** 用无副作用的公式样例在目标表格软件中确认按文本打开；普通含逗号、引号、换行的字段及合法数值仍正确导出。

## 11. 无调用的 DOM 事件包装及重复底座

**事实与证据：** EventRPC 主链已移除；[Google DomEventBus](../../../../extension/src/core/rpc/DomEventBus.ts) 与 [Bing DomEventBus](../../../../extension-bing/src/core/rpc/DomEventBus.ts) 仍只被统一导出和测试引用，没有生产消费者，合计 352 行。基线文件比对还发现双插件 `core/` 有 34 个字节完全相同的文件、单份共 3,042 行，包括第 4 项涉及的 HTTP 刷新实现。

**影响：** 无调用代码增加阅读与测试负担；同一认证缺陷需要修改两份，修复容易遗漏另一端。本项属于维护成本与抽象边界问题，不等同于运行时安全漏洞。

**修复方向：** 删除无调用包装及对应导出、测试；按实际共同调用点共享相同的 HTTP、认证和存储逻辑，避免扩大为新的通用插件框架。逐项核对删除与共享的范围。

**验收：** 全仓引用确认删除安全；保留真实 Maps XHR 转发和 Chrome 消息路径；受影响双插件通过必要的类型、生成客户端检查与运行验证。

## 12. 客户端 IP 信任边界

**事实与证据：** [get_client_ip](../../../../backend/src/app/utils/common.py) 优先信任 `CF-Connecting-IP` 与 `X-Forwarded-For`；[Nginx 模板](../../../../backend/deploy/nginx/nginx.conf) 透传这些字段。固定连接来源、改变请求头的隔离复现中，返回的客户端 IP 随之改变。

**触发与影响：** 若公网能绕过可信代理直达源站，调用者可以轮换请求头绕过 [Email Checker](../../../../backend/src/app/api/client/tools_client.py)、[验证码发送](../../../../backend/src/app/services/email_verification_service.py) 等 IP 限流。若部署入口已经限制为可信代理并重写相关头，利用条件可能不成立；当前未核实线上防火墙及代理完整配置。

**核对与修复方向：** 先确认源站是否可直连、哪些代理负责覆盖来源头，以及后端实际收到的头部链。存在缺口时，在可信代理边界重建客户端 IP 并限制源站入口。

**验收：** 从不可信来源伪造上述头部，不能改变限流身份；正常代理流量仍识别实际用户 IP。部署验证不得消耗真实付费验证额度或批量发送邮件。
