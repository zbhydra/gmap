# 插件版本管理实施计划

> 已批准的实施与验收记录。共享行为、数据规格与接口以 [插件版本管理](../tech-插件版本管理.md) 为唯一合同；本文件记录执行状态、证据与未验项。

## 已确认目标

- Admin 管理 Google Maps 与 Bing 两个插件的版本记录，发布新版时新增一条记录。
- 普通新版提醒和指定版本禁用同时支持；被禁用版本必须更新后才能开始新采集。

独立版本表、Admin 菜单与检查失败时拒绝新采集的取舍均已确认，直接按共享合同执行。

### Maps 真实环境与范围外缺口

- 普通搜索在 `current` 与 `update_available` 下均能开始并收到 HTTP 200 XHR，但响应末尾缺少 `/*""*/` 标记。既有 `src/injected/index.ts:notifyIfComplete` 因 `endsWith=false` 不发完成事件，两种状态都采到 0 条。已确认是既有采集事件缺口，本次不扩入采集器修复；只记录开始 / 请求放行，普通搜索正向采集与导出未通过。
- 照片真实页面遇到 Google `/sorry` 验证码，采集与导出按环境跳过记录。长期照片采集合同保持原验收目标。
- 真实保存列表正向与普通搜索同会话暂停 / 继续未单独执行；列表负向和媒体直接启动 / Reset 由定向入口回归覆盖，不写为真实采集通过。

### Admin 默认产物恢复

- 不注入本任务临时 API 覆盖，按现有配置执行 `pnpm build`，通过；产物确认不含隔离后端地址。运行态 API 来源为 `src/api/request.ts:API_BASE`，默认空串，因此使用相对 `/api/admin`；Vite preview 沿用既有 `/api → localhost:7600` 代理。
- 默认产物启动后，版本路由、入口与版本页模块均可加载。初次因本地 7600 后端未启动而出现验证码代理错误；经批准在空闲的本机 7600 临时转发至既有真实端点后，验证码 API 为 HTTP 200 / code 10000，真实浏览器按未登录守卫跳登录页、保留版本页回跳地址且验证码正常加载，无页面错误。完整管理页数据流程复用 U2 真实证据，本阶段未重复写版本数据或改动源配置。
- 构建、启动与浏览器记录见 [U5 证据](../../../scratch/plugin-version-u5/验收摘要.md)。

### 跨端组合与默认插件产物

- 复用各单元的采集、导出和管理 UI 证据，最小组合仅通过真实 Admin 版本路由在隔离库发布两个插件的同号版本，再由两个原生扩展的 Popup / RPC 读取各自推荐地址；仅禁用 Maps 本地版本后，Maps 为禁用、Bing 仍普通更新，重新启用 Maps 后恢复更新。页面无 JS 异常。本次自建 3 条版本和 1 个管理员已精确清理，凭据文件已删除。
- Maps 联调 dist / ZIP 含临时 API，已使用无覆盖的默认 `pnpm build` 恢复；Bing dist / ZIP 本来就是默认构建，未重复重建。两端 ZIP 均与对应 dist 逐文件一致，均不含临时隔离 API 地址。
- 默认 API 仍取仓库既有 `https://api.example.com` 占位值。加载最终默认包后，Maps SW / Popup / Dashboard 与 Bing SW / Popup 均正常运行；真实版本请求连接关闭，界面显示可重试失败态，Maps RPC 返回 null。此项只证明默认产物启动与失败呈现，未证明远端已部署新接口。

## 最少验证与交付门禁

仅改文档的阶段只执行格式、链接与内容一致性检查。实施与集成门禁：

- 后端：使用 `uv run python -m app.init.sync_database_schema --yes` 同步模型；运行直接相关真实 API 测试与 black / ruff / mypy，完成 `uv build --wheel` 和 Uvicorn 启动、健康检查。
- Admin：运行直接相关 UI 用例，执行 `pnpm build` 并启动产物，验证版本页路由可访问。
- 两插件：各执行 `pnpm check`、直接覆盖此次门控的最少测试和 `pnpm build`，加载构建产物，使用真实 Maps / Bing 页面验证门控与导出；不因本次规划要求重跑全量 E2E。
- 版本记录验证只在明确的隔离测试库进行，清理范围限于本次创建的记录。不能隔离时，报告该项环境阻塞，不能修改已有运营版本来凑验收。
- 验收记录明确区分通过、失败、环境跳过和未执行；已有且对应最终改动的完整证据可复用。

## 设计审查

跨后端、Admin 与双插件的共享禁用边界需要一次独立方案审查。审查只核对合同完整性、门控入口、数据边界和新增复杂度，不扩展到仓库全面审计；确认的阻塞项修订后由同一 reviewer 定向复验。

独立方案审查已完成，无确认阻塞项。U1、U2、U3、U4 的实施审查均已通过；整体独立审查正式通过，确认 Admin、后端与双插件的合同一致，旧机制清理、批量暂停和数据保留符合合同，组合、默认产物、ZIP 和文档证据充分。已知运行限制按上方记录保留。

## 接受边界

检查失败会阻止本次新采集；未预置检查逻辑的旧包不能被追溯禁用。这两项取舍已获确认，交付不宣称实时强制停用或自动升级。

发布和运营版本登记遵循 [生效边界](../tech-插件版本管理.md#生效边界)，本任务未执行发布或登记运营版本。
